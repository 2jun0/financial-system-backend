# 2주차 요일별 계획

## 완료 기준

다음 주 화요일까지 다음 정상 흐름이 실제로 한 번 동작하면 2주차를 완료한다.

```text
은행 A 고객 송금 요청
→ 은행 A 출금 및 출금 기록
→ 중앙 결제 거래 생성
→ 은행 B 수취 계좌 검증
→ 중앙 결제 완료
→ 은행 A 송금 성공 반영
→ 은행 B 입금 및 입금 기록
→ 양쪽 고객이 잔액과 거래 내역 조회
```

## 월요일 — 실행 기반 완성

- 개발용 Compose에 독립 DB 3개 정의
- 프로필로 필요한 DB만 실행
- 은행 애플리케이션을 `bank-a`, `bank-b` 설정으로 각각 실행
- 미정인 컬럼 자료형과 최소 인증 방식을 구현 관점에서 결정
- 은행 애플리케이션이 DB 연결 후 정상 기동되는지 확인

완료 조건:

> 은행 A와 은행 B가 동일한 은행 애플리케이션을 서로 다른 프로필과 DB로 실행할 수 있고, 개발용 DB 세 개가 준비되어 있다.

## 화요일 — 은행 도메인과 영속성 기반

- `Customer`, `Account`, `AccountTransaction` 엔티티 작성
- 거래 유형과 금액 부호 불변식 정의
- Flyway V1 스키마 작성
- 고유 제약, 외래키와 조회 인덱스 정의
- 기능 우선·기능 내부 계층형 패키지 구조 적용

완료 조건:

> 은행의 고객·계좌·거래 내역 모델과 이를 저장할 최초 스키마가 서로 일치한다.

## 수요일 — 은행 영속성 연결

- Bank A DB에 Flyway V1 적용 및 스키마 검증
- 고객·계좌·거래 내역 Repository 작성
- JPA 엔티티와 Flyway 스키마의 매핑 검증
- `bank-a` 프로필로 애플리케이션 실행 및 DB 연결 확인

완료 조건:

> Bank A 애플리케이션이 Flyway V1이 적용된 DB에 연결되고, Repository가 Spring Bean으로 정상 등록된다.

## 목요일 — 고객·계좌·거래 내역

- 최소 회원가입과 로그인
- 계좌 생성
- 시연용 고객 계좌에서 신규 계좌로 100,000원 내부 이체
- 계좌 잔액 조회
- 계좌 거래 내역 조회
- 내부 이체 시 양쪽 계좌의 잔액과 `DEBIT`, `CREDIT` 기록을 하나의 DB 트랜잭션으로 처리
- 다른 고객의 계좌를 조회하거나 사용하지 못하게 검증

완료 조건:

> 고객을 만들고 계좌를 개설하면 100,000원과 그 출처가 되는 거래 내역을 조회할 수 있다.

은행 로컬 완료 조건을 충족한 뒤 중앙 결제 기능을 시작한다.

## 금요일 — 송금 은행의 출금과 중앙 요청

- 중앙 결제 Spring Boot 프로젝트 생성 및 DB 연결 확인
- 중앙 결제 엔티티 확정 후 중앙 DB의 Flyway 최초 스키마 작성
- 송금 요청 API
- 송금액이 양의 정수인지 검증
- 계좌 소유권과 잔액 검증
- `transfer_key` 발급
- `Transfer`를 `송금중`으로 생성
- 송금 계좌 잔액 차감
- `DEBIT` 거래 기록 생성
- 위 로컬 변경을 하나의 은행 DB 트랜잭션으로 처리
- 중앙 결제에 거래 생성 요청
- 중앙 결제에서 `Settlement`를 `수취검증대기`로 생성

완료 조건:

> 은행 A가 송금을 요청하면 출금 기록과 `송금중` 거래가 생기고, 중앙 결제에 같은 `transfer_key`의 거래가 존재한다.

부분 실패를 완벽하게 해결하지 않는다. 단순한 최초 구현을 남겨 3주차 트랜잭션 경계 실험의 기반으로 사용한다.

## 토요일 — 수취 검증과 결제 완료

- 은행 B가 자기 은행의 `수취검증대기` 거래 조회
- 수취 계좌 존재 여부 확인
- 검증 결과를 중앙 결제에 전달
- 중앙 결제에서 은행 A 결제잔액 차감
- 은행 B 결제잔액 증가
- `Settlement`를 `결제완료`로 변경
- 중앙의 세 변경을 하나의 중앙 DB 트랜잭션으로 처리
- 은행 A가 결과를 조회하여 `Transfer`를 `성공`으로 변경
- 은행 B가 완료 결제를 조회
- 수취 계좌 잔액 증가
- `CREDIT` 거래 기록 생성

완료 조건:

> 중앙 결제가 완료되면 은행 A의 송금은 성공이 되고, 은행 B 고객 계좌에 입금이 반영된다.

이번 주에는 polling 주기, 커서, 페이지 처리와 다중 Pod 경쟁을 완성하지 않는다. 한 번 실행할 수 있는 단순한 조회 구조로 시작한다.

## 일요일 — 전체 흐름 연결

- 은행 A, 중앙 결제, 은행 B를 함께 실행
- 송금 요청부터 수취 입금까지 각 단계가 순서대로 호출되는지 확인
- 연결 과정에서 발견한 누락된 API와 설정 수정
- 발견한 실패 지점을 다음 주 월요일 검증 대상으로 기록

일요일에는 정상 시나리오의 완전한 검증보다 세 시스템의 연결을 우선한다. 장애 처리나 추가 거절 조건은 구현하지 않는다.

## 다음 주 월요일 — 정상 시나리오 완주

세 시스템을 함께 실행하여 `S-001 정상 은행 간 송금 성공`을 수행한다.

- 은행 A 고객 잔액이 송금액만큼 감소
- 은행 A에 `DEBIT` 기록 한 건 존재
- 은행 A의 `Transfer`가 `성공`
- 중앙 거래가 `결제완료`
- 중앙의 두 은행 결제잔액 합계가 보존
- 은행 B 고객 잔액이 송금액만큼 증가
- 은행 B에 `CREDIT` 기록 한 건 존재
- 세 시스템이 동일한 `transfer_key` 사용
- 애플리케이션 테스트 전체 실행

정상 흐름이 연결되면 2주차 핵심 구현 목표를 달성한 것으로 본다.

## 다음 주 화요일 — 기준선 확정

2주차 구현의 기준선을 확정한다.

필수 작업:

- 처음부터 환경을 다시 실행해 정상 송금 재검증
- 테스트 결과 확인
- 실행 방법 기록
- README의 현재 단계를 2주차 상태로 수정
- 단순 구현의 한계 기록
- 예상 실패 지점 기록
- 3주차에 깨뜨릴 후보 정리

여유가 있을 때만 다음을 추가한다.

- 0 이하 송금액 거절
- 고객 잔액 부족 거절
- 기본 API 오류 응답 정리
- 주요 서비스 테스트 보강

수취 계좌 없음, 결제잔액 부족, 보상과 장애 복구는 정상 흐름보다 우선하지 않는다.

## 다음 주 수요일 — 3주차 시작

다음 문제는 2주차에 해결하지 않고 3주차 이후의 관찰 대상으로 남겨도 된다.

- 은행 출금 후 중앙 요청 실패
- 중앙 결제 완료 후 은행 A 상태 반영 실패
- 중앙 결제 완료 후 은행 B 입금 반영 실패
- 같은 요청이 반복됐을 때의 중복 처리
- 동시에 여러 송금이 실행될 때의 잔액 경쟁

## 우선순위

```text
실행 기반
→ 은행 로컬 기능
→ 송금 출금
→ 중앙 결제
→ 수취 입금
→ S-001 전체 검증
```

2주차에는 많은 기능보다 정상 송금 하나의 시작부터 최종 조회까지 완주하는 것을 우선한다.
