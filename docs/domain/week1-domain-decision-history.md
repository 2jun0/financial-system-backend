# 1주차 도메인 결정 변경 이력

> 이 문서는 요구사항 논의 중에 누적된 결정 원문을 보존한다. 현재 유효한 설계는 [1주차 도메인 결정 기록](week1-domain-decisions.md)을 기준으로 한다.

## 문서 목적

금융 시스템의 구조가 은행 A와 은행 B의 직접 통신 방식에서 모의 중앙 결제 시스템 방식으로 변경되기까지 검토한 선택지, 당시 결정, 선택 이유와 변경 내용을 보존한다. 아래 항목에는 현재 구조에서 대체되거나 재검토 중인 결정도 포함되어 있다.

## 현재 결정과의 관계

- D-001~D-005, D-010~D-012의 핵심 원칙은 현재 결정 문서에 맞게 정리해 유지한다.
- D-006의 일일 대사는 한때 polling 구조에 밀려 재검토 대상이었으나, D-054에서 동기 체인의 안전망으로 다시 채택한다.
- D-007의 독립된 두 은행 인스턴스와 DB 경계는 유지하지만, 은행 간 직접 통신 전제는 D-014로 대체한다.
- D-008의 수취 은행 `200 OK` 기반 성공 기준은 D-014 도입으로 대체되었으며 새 성공 기준은 아직 결정하지 않았다.
- D-009의 `송금중` 개념은 유지하지만 직접 응답 기반 상태 전이는 재검토한다.
- D-013의 안전 우선 원칙은 유지하되, 결과 확인의 기준을 중앙 결제 거래 내역에 맞게 다시 정의해야 한다.
- D-014와 D-015는 현재 중앙 결제 구조의 출발점으로 유지한다.

## 누적 결정 원문

## D-001 — 고객과 계좌 소유 관계

> 현재 상태: 유지. 현재 결정 문서의 `고객과 계좌`에 반영했다.

### 검토한 선택지

1. 고객 도메인 없이 계좌만 관리한다.
2. 고객 식별자와 계좌 소유 관계만 관리하고 인증은 제외한다.
3. 회원가입과 로그인을 포함해 인증된 고객과 계좌 소유 관계를 관리한다.
4. 고객 인증뿐 아니라 KYC까지 포함한다.

### 당시 결정

- 고객은 회원가입할 수 있다.
- 고객은 로그인할 수 있다.
- 고객마다 시스템 내부의 고유 식별자가 존재한다.
- 한 고객은 여러 계좌를 소유할 수 있다.
- 로그인한 고객은 자신이 소유한 계좌만 조회하고 거래할 수 있다.
- 회원 탈퇴, 비밀번호 재설정, 이메일 인증, 소셜 로그인과 KYC는 범위에서 제외한다.

### 선택 이유

- 계좌 소유 관계를 명시해 거래 권한이라는 실제 금융 도메인의 중요한 규칙을 다룰 수 있다.
- 한 고객의 복수 계좌를 허용하면 고객 자신의 계좌 간 송금과 다른 고객 계좌로의 송금을 모두 실험할 수 있다.
- 회원가입과 로그인만 포함해 사용자 식별과 권한 검증은 다루되, 인증 시스템 구현이 거래 정합성·동시성·멱등성 실험보다 커지는 것을 막는다.
- KYC와 계정 복구 기능은 별도의 규제·보안 요구사항을 크게 늘리므로 8주 프로젝트의 핵심 범위에서 제외한다.

### 파생 불변식

- 모든 계좌는 정확히 한 명의 고객에게 소유되어야 한다.
- 인증된 고객은 자신이 소유하지 않은 계좌를 조회하거나 해당 계좌에서 자금을 이동시킬 수 없다.

## D-002 — 회원가입 시 계좌 자동 개설 제외

> 현재 상태: 유지.

### 당시 결정

- 회원가입 시 계좌를 자동으로 개설하지 않는다.

### 선택 이유

- 고객 가입과 금융 계좌 개설은 서로 다른 행위이며 생명주기도 다르다.
- 자동 개설은 고객이 여러 계좌를 필요에 따라 보유한다는 요구사항을 자연스럽게 표현하지 못한다.
- 계좌 개설 조건과 실패 사유를 별도로 설계하고 검증할 기회를 없앤다.

## D-003 — 시스템 경계와 외부 자금 이동

> 현재 상태: 일부 유지. 실제 금융망 제외와 신뢰성 문제라는 범위는 유지하고, 외부 경계는 모의 중앙 결제 시스템으로 구체화했다.

### 검토한 선택지

1. 입금과 출금을 계좌 잔액의 직접 증감으로만 처리한다.
2. 실제 금융망은 제외하되 외부 자금 이동을 상정하고, 그 이후의 신뢰성 문제를 시스템이 책임진다.
3. 입금과 출금을 제외하고 시스템 내부 계좌 간 송금만 처리한다.

### 당시 결정

- 시스템은 고객이 자신이 소유한 계좌를 이용해 입금, 출금 및 시스템 내부 계좌 간 송금을 수행할 수 있도록 한다.
- 실제 금융기관이나 결제망을 통한 자금 이동은 프로젝트 범위에서 제외한다.
- 입금과 출금에서는 외부 자금 이동이 발생하는 상황을 상정한다.
- 외부 자금 이동과 관련된 거래 기록, 데이터 정합성, 중복 처리 등 신뢰성 문제는 이 시스템의 책임 범위에 포함한다.

### 선택 이유

- 개인 프로젝트에서 실제 금융망을 연동하지 않고도 금융 거래의 핵심 신뢰성 문제를 재현할 수 있다.
- 입금과 출금을 단순 잔액 변경이 아니라 식별·추적 가능한 거래로 다룰 근거가 생긴다.
- 부분 실패, 중복 요청, 응답 유실과 재시도를 이후 주차의 실험으로 자연스럽게 확장할 수 있다.
- 외부 금융망의 규제와 연동 구현에 범위를 소모하지 않고 정합성·동시성·멱등성·장애 복구라는 프로젝트 목적에 집중할 수 있다.

### 파생 고려사항

- 외부 자금 이동을 식별하는 값과 동일 이동의 중복 여부를 판단하는 기준이 필요하다.
- 외부 자금 이동이 확인된 시점과 내부 거래가 완료된 시점을 구분할 필요가 있다.
- 외부 이동과 내부 반영 중 하나만 성공했을 때의 상태와 복구 책임을 이후에 정의해야 한다.

### 보류 사항

- 외부 자금 이동을 시스템에 전달하는 구체적인 통지 형식과 신뢰 방식은 아직 결정하지 않았다.
- 입금과 출금 각각에서 외부 이동과 내부 반영의 정확한 순서는 아직 결정하지 않았다.

## D-004 — 입금의 외부 자금 출처

> 현재 상태: 일부 유지. 현금 입금 제외와 다른 은행 이체라는 범위는 유지하고, 이체 경로는 중앙 결제 시스템을 거치는 방식으로 변경했다.

### 검토한 선택지

1. 외부 은행 계좌에서 이체된 돈을 입금으로 다룬다.
2. ATM이나 창구를 통해 접수된 현금을 입금으로 다룬다.
3. 외부 은행 이체와 현금 입금을 모두 다룬다.

### 당시 결정

- 입금은 외부 은행에서 시스템 내부 계좌로 이체되어 들어온 돈으로 한정한다.
- ATM이나 창구를 통한 현금 입금은 범위에서 제외한다.

### 선택 이유

- 외부 은행 이체와 현금 입금은 발생 주체와 확인 방식이 다르므로 함께 다루면 시스템 경계가 불필요하게 넓어진다.
- 외부 은행 이체만으로도 중복 통지, 지연, 응답 유실, 부분 실패와 복구 문제를 충분히 실험할 수 있다.
- 실제 금융망은 구현하지 않으면서도 외부에서 발생한 자금 이동을 내부 거래 기록과 잔액에 반영하는 책임을 명확히 할 수 있다.
- 정합성·멱등성·장애 복구라는 프로젝트 핵심에 집중하면서 8주 일정 안에서 다룰 수 있는 범위다.

### 파생 고려사항

- 외부 은행 이체 한 건을 고유하게 식별하고 중복 여부를 판단할 기준이 필요하다.
- 수취 계좌가 존재하지 않거나 입금할 수 없는 상태일 때의 처리 방식을 정의해야 한다.
- 외부 이체 사실을 어떤 주체가 어떤 형태로 통지하는지는 별도로 정의해야 한다.

### 제외 범위

- ATM 및 창구 현금 입금
- 실제 은행 간 금융망 연동
- 외부 이체의 취소와 반환은 현재 합의에 포함하지 않으며 추후 별도로 판단한다.
- 고객이 외부 거래 정보를 직접 입력하여 입금을 발생시키는 기능

### 인터페이스 원칙

- 외부 거래 정보를 입력하는 버튼이나 도구를 구현하더라도 이는 시연과 테스트를 위한 편의 기능일 뿐, 고객이 사용할 수 있는 도메인 기능으로 취급하지 않는다.

## D-005 — 외부 입금 통지의 중복 처리

> 현재 상태: 유지. 직접 통지 대신 중앙 거래 polling에 적용하도록 현재 결정 문서에서 표현을 바꿨다.

### 당시 결정

- 외부 자금 이동 한 건에는 고유한 외부 거래 ID를 부여한다.
- 동일한 자금 이동을 재전송할 때는 최초에 부여한 외부 거래 ID를 그대로 사용한다.
- 금융 시스템은 동일한 외부 거래 ID의 입금을 계좌 잔액에 한 번만 반영해야 한다.
- 동일한 외부 거래 ID로 계좌나 금액 등 거래 내용이 다르게 전달되면 정상적인 재시도가 아니라 충돌로 취급한다.

### 선택 이유

- 처리 성공 후 응답이 유실되더라도 송신 측은 안전하게 같은 통지를 재전송할 수 있다.
- 네트워크상 메시지가 여러 번 전달되는 것과 금액이 여러 번 반영되는 것을 분리할 수 있다.
- 중복 요청과 응답 유실을 다루는 5주차 멱등성 실험의 판단 기준이 된다.

### 용어 정리

- 외부 거래 ID는 재시도마다 새로 만드는 ID가 아니라 하나의 실제 자금 이동을 식별하는 안정적인 키다.
- 개별 전송 시도를 추적할 ID가 필요하다면 외부 거래 ID와 별도로 관리한다.

## D-006 — 입금 대사 주기

> 현재 상태: 재검토. 일일 대사는 현재 유효한 기능에서 제외했으며, polling·구간 재조회·누락 검증만으로 충분한지 아직 결정하지 않았다.

### 당시 결정

- 외부 이체 기록과 금융 시스템의 입금 기록을 하루에 한 번 대사한다.
- 대사는 은행 간 송금의 정상적인 완료 조건이 아니라 누락과 불일치를 사후 탐지하는 안전망으로 사용한다.

### 선택 이유

- 실시간 통지만으로 해결되지 않은 누락 입금을 탐지할 안전망이 필요하다.
- 매 거래마다 대사하지 않고 일 단위로 수행하여 실시간 처리와 사후 검증의 책임을 분리한다.
- 장애 복구와 공격적 검증을 다루는 6~7주차의 실험 대상으로 활용할 수 있다.

### 보류 사항

- 대사 실행 시각과 기준 시간대
- 어느 시간 구간의 거래를 비교할지 정하는 마감 기준과 지연 거래 처리
- 불일치 발견 시 자동 복구할지 운영 확인 대상으로 남길지

## D-007 — 외부 시스템의 배포 경계

> 현재 상태: 일부 유지. 독립된 두 은행 인스턴스와 DB 경계는 유지한다. 은행 간 직접 HTTP 통신 전제는 D-014의 중앙 결제 시스템 구조로 대체했다.

### 당시 결정

- 동일한 금융 시스템 애플리케이션을 서로 다른 은행을 나타내는 두 인스턴스로 실행한다.
- 두 은행 인스턴스는 각각 별도의 Kubernetes Pod에서 실행한다.
- 두 은행 인스턴스는 은행 식별자와 DB를 독립적으로 가진다.
- 고객, 계좌, 잔액과 거래 기록은 은행별 DB에 분리하여 저장한다.

### 검토 결과

- 같은 애플리케이션 코드나 컨테이너 이미지를 사용하는 것 자체는 외부 시스템 모의에 문제가 되지 않는다.
- 두 Pod가 같은 DB와 내부 상태를 공유하면 하나의 시스템을 수평 확장한 복제본이므로 외부 시스템 경계가 만들어지지 않는다.
- 두 Pod가 같은 코드를 사용하더라도 은행 식별자, DB, 거래 기록과 트랜잭션 경계를 독립적으로 가지면 서로 다른 두 금융 시스템으로 모의할 수 있다.
- 동일 시스템 두 인스턴스 모델은 단순 외부 통지 모의보다 외부 측 출금, 내부 측 입금과 두 시스템 간 불일치까지 범위에 들어올 수 있다.

### 선택 이유

- 같은 애플리케이션을 재사용하면서도 서로 다른 은행 사이의 HTTP 통신과 독립적인 트랜잭션 경계를 재현할 수 있다.
- 한 은행의 출금 성공과 다른 은행의 입금 실패처럼 단일 DB 트랜잭션으로 해결할 수 없는 문제를 실험할 수 있다.
- 통지 유실, 중복 처리, 재시도와 일일 대사의 필요성을 실제 상태 분리로 검증할 수 있다.
- 별도의 완전한 외부 은행 제품을 구현하지 않아도 되어 8주 프로젝트의 범위를 제한할 수 있다.

### 파생 불변식

- 한 은행 인스턴스는 다른 은행의 DB를 직접 읽거나 수정하지 않는다.
- 은행 간 상태 전달은 정의된 외부 인터페이스를 통해서만 이루어진다.
- 각 은행의 로컬 거래는 해당 은행의 DB 트랜잭션 경계 안에서만 처리된다.

### 보류 사항

- 두 은행이 항상 동등한 전체 기능을 수행할지, 한 인스턴스를 주 실험 대상으로 제한할지
- 시스템 간 HTTP 통신과 Kubernetes Service 구성은 구현 설계 단계에서 결정한다.

## D-008 — 은행 간 송금의 성공 기준

> 현재 상태: 대체. 수취 은행의 `200 OK`를 송금 은행이 직접 받는 성공 기준은 폐기했으며, 새 성공 기준은 아직 결정하지 않았다.

> 변경 이력: D-014에서 모의 중앙 결제 시스템을 두기로 결정했다. 따라서 수취 은행의 `200 OK`를 송금 은행이 직접 받는 아래 성공 기준은 현재 구조에 그대로 적용하지 않으며, 중앙 결제 시스템의 처리 흐름을 정한 뒤 다시 정의한다.

### 검토한 선택지

1. 송금 은행의 출금이 끝나면 성공으로 판단한다.
2. 수취 은행이 통지를 받으면 성공으로 판단한다.
3. 수취 은행이 입금을 반영하고 `200 OK`를 반환하면 성공으로 판단한다.
4. 일일 대사에서 양쪽 기록이 일치하면 성공으로 판단한다.

### 당시 결정

- 수취 은행은 입금 거래 기록과 계좌 잔액 반영을 자기 DB에 정상적으로 완료한 뒤 `200 OK`를 반환한다.
- 송금 은행은 수취 은행으로부터 `200 OK`를 받았을 때 은행 간 송금을 성공으로 기록한다.
- 일일 대사는 송금 성공 조건으로 사용하지 않는다.

### 선택 이유

- 송금 은행의 출금만 완료된 상태를 고객에게 성공으로 표시하는 것을 방지한다.
- 수취 은행이 요청을 단순 접수한 시점과 실제 입금 반영이 완료된 시점을 구분할 수 있다.
- 정상 거래가 일일 대사까지 완료를 기다리지 않으므로 불필요한 지연을 만들지 않는다.
- 응답 유실 후 재전송을 선택하더라도 동일 외부 거래 ID와 수취 은행의 멱등 처리를 통해 중복 반영을 방지할 수 있다.

### 파생 불변식

- 수취 은행은 입금 반영이 완료되지 않은 거래에 `200 OK`를 반환해서는 안 된다.
- 송금 은행이 성공으로 기록한 거래는 수취 은행에 동일한 외부 거래 ID의 완료된 입금 기록이 존재해야 한다.
- 동일한 외부 거래 ID가 재전송되어도 수취 계좌 잔액은 한 번만 증가해야 한다.

### 보류 사항

- `200 OK` 이외의 응답과 네트워크 오류를 재시도 가능 실패와 영구 실패로 구분하는 규칙
- 모든 재시도가 실패했을 때의 최종 상태와 복구 방식

## D-009 — 은행 간 송금의 중간 상태

> 현재 상태: 일부 유지. `송금중`이라는 결과 불명 상태는 유지한다. 수취 은행 직접 응답을 사용한 진입·종료 조건은 폐기했으며 새 조건은 아직 결정하지 않았다.

> 변경 이력: `송금중`이라는 결과 불명 상태는 유지한다. 다만 수취 은행과의 직접 통신을 전제로 한 상태 전이 조건은 D-014의 중앙 결제 시스템 흐름을 정한 뒤 다시 정의한다.

### 당시 결정

- 송금 은행의 출금은 완료됐지만 수취 은행의 `200 OK`를 아직 받지 못한 거래는 `송금중` 상태로 표시한다.
- `송금중`은 성공이나 실패가 아직 확정되지 않은 상태다.
- 은행 간 송금 전체를 하나의 로컬 DB 트랜잭션으로 묶지 않는다.
- 각 은행은 자기 DB의 작업만 로컬 트랜잭션으로 처리한다.

### 선택 이유

- 두 은행이 독립 DB를 사용하므로 송금 은행의 출금과 수취 은행의 입금을 하나의 로컬 DB 트랜잭션으로 원자적으로 처리할 수 없다.
- 송금 은행에서 출금된 직후 수취 은행의 처리 결과가 불확실한 현실을 숨기지 않고 명시적으로 표현할 수 있다.
- 네트워크 timeout이나 응답 유실 상황에서 실제 입금 여부가 확인되기 전에 거래를 실패 또는 성공으로 단정하는 것을 방지한다.
- `송금중` 거래를 재시도와 일일 대사의 대상으로 식별할 수 있다.

### 상태 전이 초안

```text
송금중 ── 수취 은행 200 OK 수신 ──> 성공
```

### 파생 불변식

- 수취 은행의 처리 결과를 확인하지 못한 거래는 성공으로 표시해서는 안 된다.
- `송금중` 상태라는 이유만으로 송금 은행의 출금을 다시 실행해서는 안 된다.
- `송금중` 거래를 재전송한다면 최초 외부 거래 ID를 유지해야 한다.

### 보류 사항

- 출금 전에 존재할 수 있는 요청 또는 검증 상태
- `송금중` 거래의 재시도가 모두 실패했을 때 이동할 상태
- 송금을 완료할 수 없다고 판단했을 때 출금액을 복구하는 방식
- 자동 재시도를 사용할지 여부와 재시도 정책

## D-010 — 송금중 금액의 처리 방식

> 현재 상태: 원칙 유지. 선출금 후 확정 실패에만 보상한다는 원칙은 유지한다. 아래의 수취 은행 직접 확인과 대사 관련 표현은 당시 구조의 설명이며, 현재의 실패 확정 근거는 아직 결정하지 않았다.

### 검토한 선택지

1. 송금 시작 시 금액을 출금하고, 확정 실패 시 별도의 보상 거래로 반환한다.
2. 송금 시작 시 금액을 보류하고, 성공 시 최종 출금하거나 확정 실패 시 보류를 해제한다.

### 당시 결정

- 첫 번째 방식인 선출금 후 보상 거래 방식을 선택한다.
- 송금 시작 시 출금을 한 번 실행하고 금액을 `송금중`으로 추적한다.
- 수취 은행의 미입금이 확정된 경우에만 별도의 보상 거래로 반환한다.
- 결과를 알 수 없는 timeout이나 응답 유실만으로 보상하지 않는다.

### 선택 이유

- 이 프로젝트는 돈을 다루는 시스템에서 부분 실패, 동시성, 응답 유실 같은 장애를 재현하고 데이터 정합성과 신뢰성을 지키는 설계와 복구 방법을 시도하는 데 목적이 있다.
- 선출금 방식은 독립 DB 사이의 출금 후 입금 실패, 결과 불명, 재시도, 멱등 처리, 보상 거래와 대사를 핵심 실험 대상으로 직접 드러낸다.
- 보류 방식은 장부 잔액과 사용 가능 잔액의 구분, 보류·확정·해제 생명주기와 계좌 상태 관리까지 다룰 수 있다는 장점이 있다.
- 그러나 이 프로젝트는 완전한 은행 장부나 금액 예약 시스템을 재현하는 것이 주목적이 아니며, 보류 모델의 추가 복잡성은 8주 안에 핵심 신뢰성 문제를 깊게 검증하는 데 부담이 된다고 판단했다.

### 선택하지 않은 대안의 가치

- 보류 방식은 잘못된 설계가 아니라 다른 문제에 초점을 둔 합리적인 대안이다.
- 선출금 방식에서 고객 경험이나 보상 복구의 한계가 확인되면 후속 개선안으로 다시 비교할 수 있다.

### 파생 불변식

- 하나의 송금에 대한 출금은 한 번만 실행되어야 한다.
- 보상은 수취 은행에 입금되지 않았음이 확정된 송금에 한 번만 실행되어야 한다.
- 성공한 송금에는 보상 거래가 존재해서는 안 된다.
- `송금중`인 금액을 포함해 자금의 위치를 추적할 수 있어야 한다.

## D-011 — 외부 입금의 확정 거절 사유

> 현재 상태: 조건 유지. 거절 조건은 유지하지만 어느 구성요소가 거절을 기록하고 전달할지는 아직 결정하지 않았다.

### 당시 결정

수취 은행은 다음 경우 외부 입금을 반영하지 않고 확정적으로 거절한다.

- 수취 계좌가 존재하지 않는 경우
- 금액이 유효하지 않은 경우
- 동일한 외부 거래 ID가 기존 요청과 다른 내용으로 전달된 경우

### 제외 범위

- 계좌 정지 상태와 그에 따른 입금 제한
- 계좌 삭제 또는 해지 생명주기
- 통화 정보, 통화 검증, 외화 및 환전
- 송신 은행의 등록, 인증 및 유효성 검증

### 선택 이유

- 수취 계좌가 없으면 입금 대상을 확정할 수 없다.
- 유효하지 않은 금액은 잔액과 거래 기록의 정합성을 훼손할 수 있다.
- 모든 금액을 원화로 가정하고 통화 자체를 모델링하지 않아 통화 변환과 환율 문제를 프로젝트 범위에서 제외한다.
- 동일한 외부 거래 ID의 내용 충돌은 정상 재시도가 아니므로 금액을 반영해서는 안 된다.
- 계좌 정지·삭제 상태를 제외하여 거래 신뢰성이라는 핵심 범위에 집중한다.
- 두 은행 인스턴스는 신뢰된 통신 주체라고 가정하고 은행 인증 기능을 별도로 구현하지 않는다.

### 오류 분류

- 위 사유는 네트워크 오류, timeout, `5xx`와 달리 수취 은행이 입금하지 않았음을 명확히 확인한 확정 거절이다.
- 네트워크 오류, timeout과 `5xx`는 입금 여부를 단정하지 않고 결과 불명 또는 재시도 대상으로 취급한다.

### 파생 불변식

- 확정 거절된 외부 거래는 수취 계좌 잔액을 변경해서는 안 된다.

### 보류 사항

- 유효 금액의 최솟값, 최댓값과 표현 단위
- 확정 거절 사실과 거절 사유를 수취 은행에 어떤 형태로 기록할지
- 확정 거절된 외부 거래 ID를 재수신했을 때 이전 거절을 유지할지 다시 검증할지

## D-012 — 계좌 잔액과 거래 기록의 관계

> 현재 상태: 유지.

### 검토한 선택지

1. 계좌에 현재 잔액만 저장한다.
2. 현재 잔액을 저장하지 않고 거래 기록을 매번 합산한다.
3. 거래 기록과 현재 잔액을 모두 저장한다.

### 당시 결정

- 계좌에 현재 잔액을 저장한다.
- 계좌의 금액 변동을 설명할 수 있는 거래 기록도 함께 저장한다.
- 거래 기록은 잔액의 근거이며, 현재 잔액은 빠른 조회와 거래 처리를 위해 저장하는 값으로 본다.

### 선택 이유

- 거래 기록이 있어야 자금 이동을 추적하고 은행 간 기록을 대사할 수 있다.
- 거래 기록으로 다시 계산한 값과 현재 잔액을 비교하여 내부 정합성을 검증할 수 있다.
- 거래마다 전체 기록을 합산하면 조회와 거래 처리 비용이 증가하므로 현재 잔액을 별도로 저장한다.
- 신뢰성과 검증 가능성을 유지하면서도 잔액 조회와 동시 거래 처리의 성능을 확보할 수 있다.

### 파생 불변식

- 계좌의 현재 잔액은 그 계좌에 반영된 거래 기록으로 설명할 수 있어야 한다.
- 거래 기록을 삭제하거나 덮어써서 현재 잔액의 변동 근거를 없애서는 안 된다.

### 파생 고려사항

- 현재 잔액과 거래 기록은 같은 정보를 일부 중복해서 가지므로 두 값이 어긋날 가능성을 제어해야 한다.
- 은행 간 거래 대사와 계좌 잔액·거래 기록 간 내부 정합성 검증은 목적과 비교 대상이 다르므로 구분할 필요가 있다.

## D-013 — 송금 결과를 끝내 확인할 수 없는 경우

> 현재 상태: 안전 원칙만 유지. 결과 불명 시 `송금중` 유지와 보상 금지 원칙은 유효하다. 수취 은행 직접 확인과 대사를 전제로 한 복구 방식은 현재 구조에 적용하지 않는다.

### 당시 결정

- 재전송과 대사가 모두 실패하여 수취 은행의 처리 결과를 확인할 수 없는 거래는 `송금중` 상태를 유지한다.
- 재전송 횟수를 모두 사용했다는 사실이나 대사 조회가 실패했다는 사실만으로 송금을 실패 처리하지 않는다.
- 수취 은행의 미입금이 확정되지 않은 거래는 출금액을 보상하지 않는다.

### 선택 이유

- 재전송 한도 초과는 거래 실패가 아니라 통신을 통해 결과를 확인하지 못한 상태를 의미한다.
- 결과를 알 수 없는 상태에서 출금을 보상하면, 지연된 요청이 나중에 수취 은행에 반영되어 송금자와 수취인 양쪽에 금액이 남을 수 있다.
- 거래를 끝내는 것보다 근거 없는 중복 지급을 방지하는 안전성을 우선한다.

### 파생 불변식

- 수취 은행의 처리 결과를 확인할 수 없다는 이유만으로 `송금중` 거래를 `실패`로 변경해서는 안 된다.
- 수취 은행의 미입금이 확정되지 않은 거래에는 보상 거래를 실행해서는 안 된다.

### 보류 사항

- 재전송 횟수와 간격
- 대사 실패 시 재실행 주기와 부분 처리 재개 방식
- 장기간 `송금중` 상태인 거래의 경보 및 운영 절차

## D-014 — 모의 중앙 결제 시스템 도입

> 현재 상태: 유지. 현재 구조를 정의하는 결정이다.

### 검토한 선택지

1. 두 은행 인스턴스가 서로 직접 HTTP로 송금 요청을 전달한다.
2. 두 은행 사이에 기능을 제한한 모의 중앙 결제 시스템을 둔다.
3. 블록체인 기반 공동 원장을 구현한다.

### 당시 결정

- 은행 간 송금은 송금 은행과 수취 은행 사이의 직접 호출로 처리하지 않는다.
- 두 은행 사이에 모의 중앙 결제 시스템을 둔다.
- 모의 중앙 결제 시스템은 은행 인스턴스와 분리된 논리적 시스템 경계를 가진다.
- 블록체인 기반 공동 원장은 도입하지 않는다.

### 선택 이유

- 실제 은행 간 송금이 공동망이나 중앙 결제 인프라를 거치는 구조를 반영하여 프로젝트의 현실성과 설명력을 높인다.
- 중앙 결제 시스템이 존재하더라도 은행의 로컬 계좌 DB와 외부 결제 결과를 하나의 트랜잭션으로 묶을 수 없으므로, 부분 실패·응답 유실·멱등성·대사라는 프로젝트의 핵심 문제는 남는다.
- 프로젝트의 초점을 결제망 자체의 구현이 아니라 외부 결제망에 참가하는 은행 백엔드의 정합성 유지와 복구에 둘 수 있다.
- 블록체인은 합의, 공동 원장 운영과 거버넌스 문제를 추가하여 8주 프로젝트의 핵심 범위를 벗어난다.

### 제외 범위

- 실제 중앙은행 계좌와 자금 이동
- 은행 간 유동성 관리와 담보
- 차액결제와 법적 결제완결성 구현
- 실제 금융망 연동과 ISO 20022 전체 규격 구현
- 블록체인 합의와 분산 원장 운영

### 재검토가 필요한 기존 결정

- D-006의 일일 대사에서 무엇과 무엇을 비교할지
- D-008의 은행 간 송금 성공 기준
- D-009의 `송금중` 진입 및 종료 조건
- D-013에서 송금 결과를 확인하는 권위 있는 근거
- 수취 은행과의 직접 통신을 전제로 작성한 송금 시나리오

### 보류 사항

- 모의 중앙 결제 시스템이 기록할 거래 상태와 상태별 의미
- 송금 은행, 중앙 결제 시스템과 수취 은행 사이의 요청 및 응답 순서
- 중앙 결제 시스템이 송금 성공을 확정하는 시점
- 거래 상태조회와 재전송 인터페이스
- 대사의 비교 대상과 불일치 처리 원칙
- 모의 중앙 결제 시스템의 배포 단위와 데이터 저장 방식

## D-015 — 중앙 결제 거래 내역의 주기적 조회

> 현재 상태: 일부 유지. 은행별 polling과 로컬 멱등 반영은 유지하지만, 중앙 시스템이 거래 내역만 보관한다는 역할은 D-019의 결제 최종성 소유와 D-021의 은행별 결제계좌 관리로 대체했다.

### 검토한 선택지

1. 중앙 결제 시스템은 은행 간 결제 거래 내역만 관리하고, 각 은행이 자신과 관련된 내역을 주기적으로 조회한다.
2. 중앙 결제 시스템이 은행별 결제 계좌와 잔액까지 관리한다.
3. 중앙 결제 시스템이 각 은행 고객의 계좌와 거래 내역까지 관리한다.

### 당시 결정

- 중앙 결제 시스템은 고객 계좌가 아니라 은행 간 결제 거래 내역을 관리한다.
- 고객 계좌, 고객 잔액과 고객 계좌의 거래 내역은 각 은행이 독립적으로 관리한다.
- 각 은행은 중앙 결제 시스템에서 자신과 관련된 결제 거래 내역을 주기적으로 조회한다.
- 각 은행은 조회한 중앙 결제 거래를 자기 로컬 거래 기록에 반영한다.
- 중앙 결제 시스템의 거래 내역은 은행 간 결제 거래를 확인하는 기준으로 사용한다.

### 선택 이유

- 중앙 결제 시스템이 고객 계좌까지 소유하여 은행의 독립적인 데이터 경계가 사라지는 것을 방지한다.
- 응답이나 통지가 유실되더라도 은행이 중앙 결제 시스템의 기록을 다시 조회하여 누락된 거래를 확인할 수 있다.
- 직접 통신의 불확실성을 영속적인 중앙 기록과 은행 로컬 기록 사이의 동기화 문제로 바꾸어 복구 기준을 명확히 할 수 있다.
- 은행별 결제 계좌와 유동성 관리까지 구현하지 않아 8주 프로젝트의 범위를 유지한다.

### 파생 불변식

- 한 은행은 다른 은행의 고객 계좌 DB를 직접 읽거나 수정해서는 안 된다.
- 동일한 중앙 결제 거래를 여러 번 조회하더라도 고객 계좌와 로컬 거래 기록에는 한 번만 반영되어야 한다.
- 은행의 로컬 거래 기록은 어떤 중앙 결제 거래를 근거로 반영했는지 추적할 수 있어야 한다.
- 중앙 결제 거래 내역을 조회하지 못했다는 이유만으로 고객 계좌에 임의의 입금이나 보상을 실행해서는 안 된다.

### 보류 사항

- 조회 주기와 한 번에 조회할 거래 수
- 마지막 조회 위치를 식별하고 저장하는 방식
- 여러 은행 Pod가 동일한 거래를 동시에 조회한 경우의 처리 방식
- 중앙 거래 조회와 로컬 DB 반영 사이의 부분 실패 복구 방식
- 정상적인 거래 반영용 polling과 일일 대사의 정확한 역할 구분

## D-016 — 중앙 결제 구조에서 송금 성공의 기준

> 현재 상태: 대체. 수취 은행의 로컬 입금 완료를 송금 성공 기준으로 삼은 결정은 D-019의 중앙 결제 완료 기준으로 대체했다.

### 검토한 선택지

1. 중앙 결제 시스템에 거래가 기록되면 송금 성공으로 확정한다.
2. 수취 은행이 수취 계좌에 입금을 완료한 사실을 중앙 결제 시스템을 통해 확인할 수 있을 때 송금 성공으로 확정한다.
3. 중앙 처리 완료와 수취 계좌 반영 완료를 서로 다른 성공 단계로 관리한다.

### 결정

- 두 번째 방식을 선택한다.
- 중앙 결제 시스템에 거래가 기록되었다는 사실만으로는 송금 성공으로 확정하지 않는다.
- 수취 은행이 수취 계좌에 입금을 완료한 사실을 중앙 결제 시스템을 통해 확인할 수 있을 때 송금 성공으로 확정한다.
- 수취 은행이 입금을 반영하지 않고 확정적으로 거절한 거래는 성공으로 확정하지 않는다.

### 선택 이유

- 중앙 결제 거래가 존재하더라도 수취 은행이 계좌를 확인하는 과정에서 입금을 거절할 수 있다.
- 중앙 기록 생성만으로 성공 처리하면 수취 계좌에 금액이 반영되지 않았는데도 고객에게 성공으로 표시할 수 있다.
- 중앙 처리와 수취 반영을 두 개의 성공 단계로 나누면 상태와 고객에게 노출되는 의미가 복잡해지지만, 현재 프로젝트에서는 이를 구분해야 할 필요성이 크지 않다.
- 실제 수취 계좌 반영을 성공 기준으로 삼아 고객에게 표시하는 송금 결과의 의미를 명확하게 유지한다.

### 파생 불변식

- 성공으로 확정된 송금에는 수취 은행의 동일한 외부 거래 ID에 대한 완료된 입금 기록이 존재해야 한다.
- 수취 은행의 처리 결과가 아직 확인되지 않은 송금을 성공으로 표시해서는 안 된다.

### 보류 사항

- 수취 은행의 입금 완료 또는 확정 거절 결과를 중앙 결제 시스템에 반영하는 방식
- 중앙 결제 시스템과 각 은행이 사용할 구체적인 거래 상태명과 상태 전이

## D-017 — 수취 은행 처리 결과의 전달 주체

> 현재 상태: 재검토. 중앙 시스템이 수취 은행의 입금 결과를 받아 결제를 확정하는 구조는 D-019에서 폐기했다. 중앙 결제 전 수취 가능 여부를 확인하는 방식은 별도로 결정한다.

### 검토한 선택지

1. 수취 은행이 로컬 처리를 완료한 뒤 중앙 결제 시스템에 결과를 전달한다.
2. 중앙 결제 시스템이 수취 은행에 처리 결과를 반복 조회한다.
3. 송금 은행이 수취 은행에 직접 처리 결과를 조회한다.

### 결정

- 첫 번째 방식을 선택한다.
- 수취 은행은 자기 로컬 처리를 완료한 뒤 입금 완료 또는 확정 거절 결과를 중앙 결제 시스템에 전달한다.
- 중앙 결제 시스템이나 송금 은행이 수취 은행에 처리 결과를 조회하는 방식은 사용하지 않는다.

### 선택 이유

- 수취 은행이 자기 로컬 입금의 완료 또는 거절 여부를 가장 정확히 판단할 수 있다.
- 중앙 결제 시스템이 모든 수취 은행의 내부 처리 상태를 계속 조회하는 책임을 갖지 않아도 된다.
- 송금 은행과 수취 은행 사이의 직접 통신을 다시 만들지 않고 중앙 결제 시스템을 은행 간 거래 결과의 기준으로 유지할 수 있다.

### 파생 불변식

- 수취 은행은 로컬 입금이 완료되지 않은 거래를 입금 완료로 전달해서는 안 된다.
- 수취 은행의 확정 거절 결과가 존재하는 거래에는 수취 계좌의 입금이 존재해서는 안 된다.

### 보류 사항

- 수취 은행의 로컬 처리 완료 후 중앙 결제 시스템으로 결과를 전달하기 전에 장애가 발생한 경우의 복구 방식
- 결과 전달 요청 또는 응답이 유실된 경우의 재시도와 멱등 처리 방식

## D-018 — 수취 은행 처리 결과 전달 실패의 복구

> 현재 상태: 일부 대체. 수취 은행이 입금 결과를 중앙에 보고해 결제를 끝내는 전제는 폐기했다. 완료된 중앙 결제를 수취 은행이 polling하고 로컬에 멱등하게 반영한다는 복구 원칙은 유지한다.

### 검토한 선택지

1. 중앙 결제 시스템이 최종 결과를 받을 때까지 해당 거래를 수취 은행의 polling 결과에 계속 포함하고, 수취 은행이 기존 로컬 결과를 다시 전달한다.
2. 수취 은행이 입금 또는 거절과 함께 별도의 결과 전달 대기 기록을 저장하고 독립 작업이 전달을 재시도한다.
3. polling 재제공과 별도의 결과 전달 대기 기록을 함께 사용한다.

### 결정

- 첫 번째 방식을 선택한다.
- 중앙 결제 시스템은 수취 은행의 최종 처리 결과를 확인할 때까지 해당 거래를 수취 은행의 polling 결과에 다시 포함할 수 있다.
- 수취 은행은 같은 거래를 다시 조회하면 외부 거래 ID로 기존 로컬 처리 결과를 확인한다.
- 기존 입금 또는 거절 처리를 반복하지 않고, 확인한 기존 결과만 중앙 결제 시스템에 다시 전달한다.

### 선택 이유

- 이미 선택한 polling 구조와 외부 거래 ID의 멱등성을 복구에도 사용할 수 있다.
- 별도의 결과 전달용 outbox와 처리 작업을 추가하지 않아 현재 프로젝트의 범위를 제한할 수 있다.
- 수취 은행이 입금을 완료한 뒤 결과 전달 전에 중단되더라도 중앙 거래가 결과 불명으로 영구히 누락되는 것을 방지할 수 있다.

### 파생 불변식

- 동일한 중앙 결제 거래가 polling에서 여러 번 반환되어도 수취 계좌 잔액은 한 번만 변경되어야 한다.
- 이미 로컬 처리한 거래를 다시 조회한 경우 기존 처리 결과와 다른 결과를 중앙 결제 시스템에 전달해서는 안 된다.

### 보류 사항

- polling 주기와 한 번에 조회할 거래 수
- 최종 결과를 받지 못한 거래를 polling 결과에 포함하는 구체적인 조회 방식
- 결과 재전달 횟수와 간격

## D-019 — 중앙 결제 시스템의 결제 최종성 소유

> 현재 상태: 유지. 중앙 결제 시스템의 존재 목적과 권위 있는 결과를 정의한다.

### 결정

- 중앙 결제 시스템은 은행 간 결제가 완료됐는지 또는 거절됐는지를 확정하는 권위 있는 시스템이다.
- 중앙 시스템에서 완료된 결제는 최종적인 결과이며, 개별 은행의 로컬 처리 지연이나 실패로 되돌리지 않는다.
- 송금 은행은 중앙 결제 시스템의 완료 결과를 근거로 송금을 성공 처리한다.
- 송금 은행은 중앙 결제 시스템의 거절 결과를 확인한 경우에만 출금액을 보상한다.
- 수취 은행은 완료된 중앙 결제를 자기 고객 계좌에 멱등하게 반영한다.
- 수취 은행의 고객 계좌 반영 실패는 중앙 결제 실패가 아니라 수취 은행이 복구해야 할 로컬 미반영 문제로 다룬다.

### 선택 이유

- 은행 간 자금 이동의 결과를 개별 은행의 로컬 상태와 응답에 의존하면 장애나 결과 불명 상황에서 송금 은행이 보상 여부를 안전하게 결정하기 어렵다.
- 중앙 시스템이 최종 결과를 소유해야 모든 참가 은행이 같은 기준으로 상태를 수렴시킬 수 있다.
- 완료된 결제를 되돌리지 않으면 수취 은행의 지연된 입금과 송금 은행의 보상이 함께 발생하여 돈이 중복되는 것을 방지할 수 있다.
- 고객 계좌는 각 은행이 계속 소유하되 은행 간 결제 결과만 중앙화하여 데이터 소유 경계를 유지한다.

### 파생 불변식

- 중앙 결제 시스템이 완료로 확정한 거래를 개별 은행이 실패나 거절로 변경해서는 안 된다.
- 중앙 결제 시스템이 완료로 확정한 거래에는 송금 은행의 보상 거래가 존재해서는 안 된다.
- 중앙 결제 시스템이 거절로 확정하지 않은 거래를 송금 은행이 임의로 보상해서는 안 된다.
- 수취 은행은 동일한 완료 결제를 고객 계좌에 한 번만 반영해야 한다.

### 재검토되는 기존 결정

- D-015에서 중앙 시스템이 은행 간 거래 내역만 관리한다고 한 범위
- D-016에서 수취 은행의 고객 계좌 입금 완료를 송금 성공 기준으로 삼은 결정
- D-017과 D-018에서 수취 은행이 로컬 입금 결과를 중앙 시스템에 보고하여 결제를 끝낸다는 처리 순서

### 보류 사항

- 중앙 결제 상태와 각 은행의 로컬 거래 상태

## D-020 — 참가 은행의 신뢰 모델

> 현재 상태: 유지. 중앙 결제 시스템이 방어할 장애 범위와 프로젝트에서 제외할 위협을 정의한다.

### 검토한 선택지

1. 참가 은행은 정상 주체이지만 애플리케이션과 네트워크 장애가 발생할 수 있다고 가정한다.
2. 참가 은행이 허위 거래를 만들거나 처리 결과를 조작하는 악의적인 주체일 수 있다고 가정한다.

### 결정

- 첫 번째 방식을 선택한다.
- 참가 은행은 사전에 식별되고 허용된 정상 주체이며 의도적으로 허위 거래를 만들지 않는다고 가정한다.
- 참가 은행의 애플리케이션, 프로세스와 네트워크에는 언제든 장애가 발생할 수 있다고 가정한다.
- 서버 중단, 응답 유실, 메시지 중복, 처리 지연, 순서 변경과 동시 처리를 시스템이 견뎌야 한다.

### 선택 이유

- 금융 시스템에서는 개별 은행 시스템의 장애를 간과할 수 없으므로 은행의 로컬 상태나 일시적인 응답에 전역 결제 결과를 의존해서는 안 된다.
- 중앙 결제 시스템이 결제 최종성을 소유하면 참가 은행은 장애 복구 후 같은 기준을 조회하여 로컬 상태를 수렴시킬 수 있다.
- 악의적인 참가자까지 포함하면 은행별 결제 잔액, 메시지 서명, 부인 방지, 규제와 감사 절차가 필요해져 8주 프로젝트의 핵심 범위를 벗어난다.

### 파생 불변식

- 한 은행의 프로세스 장애나 네트워크 단절이 완료된 중앙 결제를 실패로 바꾸어서는 안 된다.
- 같은 거래의 중복·지연·순서 변경 메시지가 서로 다른 중앙 결제 결과를 만들어서는 안 된다.
- 참가 은행이 장기간 응답하지 않더라도 중앙 결제 시스템은 결과를 추측해서는 안 된다.

### 제외 범위

- 참가 은행의 허위 거래 생성과 고의적인 결과 조작
- 메시지 전자서명과 부인 방지
- 금융기관 규제, 법적 책임과 외부 감사 절차

## D-021 — 은행별 결제계좌와 수취 계좌 사전 검증

> 현재 상태: 유지. 중앙 결제 완료의 원장 근거와 수취 은행 검증을 필수 선행 조건으로 정의한다.

### 검토한 선택지

1. 중앙 시스템이 은행별 결제계좌와 잔액을 관리하고, 수취 은행의 고객 계좌 검증 후 결제를 실행한다.
2. 은행별 결제잔액 없이 충분한 유동성을 가정하고 결제 완료 상태만 기록한다.
3. 담보, 일중대출, 차액결제와 결제 대기열까지 포함한 유동성 시스템을 구현한다.

### 결정

- 첫 번째 방식을 선택한다.
- 중앙 결제 시스템은 참가 은행마다 하나의 결제계좌와 현재 결제잔액을 관리한다.
- 고객 계좌는 각 은행이 소유하며 중앙 결제계좌와 구분한다.
- 송금 은행 결제계좌 차감, 수취 은행 결제계좌 증가와 결제 완료 기록은 하나의 중앙 DB 트랜잭션으로 처리한다.
- 송금 은행의 결제잔액이 부족하면 중앙 결제를 거절한다.
- 중앙 결제 전에 수취 은행이 수취 고객 계좌가 존재하여 입금 대상이 될 수 있는지 반드시 검증한다.
- 수취 가능 확인은 실제 고객 계좌 입금이 아니며 고객 잔액을 변경하지 않는다.
- 수취 계좌가 존재하지 않는다고 확정되면 중앙 결제를 거절한다.
- 수취 은행의 장애나 통신 실패로 검증 결과를 확인하지 못한 경우에는 거절로 추측하지 않는다.

### 선택 이유

- 결제잔액의 원자적인 차감과 증가가 있어야 중앙 결제 완료가 단순한 상태 문구가 아니라 실제 은행 간 원장 변동을 뜻한다.
- 중앙 결제계좌는 고객 계좌가 아니므로 고객 잔액에 대한 각 은행의 소유권을 유지할 수 있다.
- 수취 계좌를 검증하지 않고 결제를 완료하면 수취 은행이 고객에게 귀속시킬 수 없는 자금을 받게 된다.
- 사전 검증과 실제 고객 입금을 분리하면 중앙 결제의 최종성을 유지하면서 결제 후 로컬 입금 장애를 멱등하게 복구할 수 있다.
- 단순한 결제잔액 모델은 트랜잭션, 동시성, 잔액 부족과 중복 결제를 실험하면서도 복잡한 유동성 관리까지 범위가 확대되는 것을 막는다.

### 파생 불변식

- 중앙 결제 전후 모든 은행 결제계좌 잔액의 합계는 같아야 한다.
- 하나의 거래가 송금 은행 결제계좌에서 두 번 차감되거나 수취 은행 결제계좌에 두 번 증가해서는 안 된다.
- 수취 은행의 수취 가능 확인이 없는 거래를 결제 완료로 변경해서는 안 된다.
- 수취 불가로 확정된 거래는 은행 결제계좌와 수취 고객 계좌를 변경해서는 안 된다.
- 수취 가능 확인만으로 수취 고객 계좌 잔액을 증가시켜서는 안 된다.

### 제외 범위

- 담보와 일중대출
- 당좌대월
- 차액결제
- 결제 우선순위와 유동성 대기열

### 보류 사항

- 수취 가능 확인의 유효 기간과 결제 전 재검증 여부
- 은행 결제계좌의 초기 잔액을 설정하는 테스트·운영 방식

## D-022 — 수취 계좌 사전 검증의 polling 방식

> 현재 상태: 유지. 수취 은행이 검증 대기 거래를 발견하고 결과를 전달하는 통신 방향을 정의한다.

### 검토한 선택지

1. 수취 은행이 중앙 결제 시스템을 polling하여 검증 대기 거래를 조회하고 결과를 전달한다.
2. 중앙 결제 시스템이 수취 은행의 검증 API를 직접 호출한다.
3. 중앙 직접 호출을 우선 사용하고 polling을 복구 수단으로 함께 사용한다.

### 결정

- 첫 번째 방식을 선택한다.
- 수취 은행은 중앙 결제 시스템을 polling하여 자기 은행의 수취 계좌 검증 대기 거래를 조회한다.
- 수취 은행은 수취 가능 또는 수취 불가 결과를 중앙 결제 시스템에 전달한다.
- 중앙 결제 시스템은 수취 은행을 직접 호출하여 계좌를 검증하지 않는다.
- 수취 은행이 중단됐거나 통신할 수 없으면 거래는 검증 대기 상태를 유지한다.

### 선택 이유

- 수취 은행의 가동 여부와 중앙 결제 요청 처리를 시간적으로 분리할 수 있다.
- 수취 은행이 복구한 뒤 중앙에 남은 검증 대기 거래를 다시 조회하여 처리를 재개할 수 있다.
- 결제 완료 거래를 고객 계좌에 반영할 때도 polling을 사용하므로 동일한 통신 방향과 복구 원칙을 재사용할 수 있다.
- 중앙 시스템이 각 은행의 호출 주소, timeout과 직접 호출 재시도 작업을 관리하지 않아도 된다.

### 파생 불변식

- 같은 검증 대기 거래가 여러 번 조회돼도 서로 다른 검증 결과로 중앙 결제가 중복 또는 변경되어서는 안 된다.
- 같은 수취 가능 결과가 여러 번 전달돼도 은행별 결제계좌 이동은 한 번만 실행되어야 한다.
- 수취 은행의 응답이 없다는 이유만으로 수취 불가나 결제 거절을 확정해서는 안 된다.

### 보류 사항

- polling 주기와 한 번에 조회할 검증 대기 거래 수
- 여러 수취 은행 Pod가 같은 검증 대기 거래를 동시에 조회한 경우의 처리 방식
- 수취 가능 또는 불가 결과 전달 요청의 재시도 간격

## D-023 — MVP 송금 기능, 금액 규칙과 최소 상태

> 현재 상태: 일부 유지. MVP 송금 범위와 상태는 유지하고, 계좌 생성 시 자금 지급 방식은 D-030으로 대체했다.

### 결정

- 고객은 자신이 소유한 계좌에서 다른 은행 계좌로 보내는 송금을 직접 요청한다.
- 고객이 별도로 실행하는 입금·출금 기능은 구현하지 않는다.
- 같은 은행 계좌 사이의 송금은 MVP에서 제외한다.
- 계좌를 개설하면 시연용 테스트 자금을 자동 지급하고, 그 잔액 변동을 설명하는 초기 자금 거래 기록을 남긴다.
- 송금 은행이 고객 계좌를 차감하면 출금 기록을 남긴다.
- 중앙 결제가 완료된 거래를 수취 은행이 고객 계좌에 반영하면 입금 기록을 남긴다.
- 고객은 자신이 소유한 계좌의 출금·입금 기록을 조회할 수 있다.
- 송금액은 0보다 큰 양의 정수만 허용한다.
- 고객 계좌 잔액이 부족하면 송금 요청을 거절한다.
- 중앙 시스템의 송금 은행 결제잔액이 부족하면 중앙 결제를 거절한다. 다만 MVP 정상 흐름에서는 충분한 결제잔액을 가정하고 유동성 회복 절차는 다루지 않는다.
- 송금 은행의 최소 거래 상태는 `송금중`, `성공`, `실패`이다.
- 중앙 결제의 최소 상태는 `수취검증대기`, `결제완료`, `결제거절`이다.
- 중앙 결제 완료를 확인하면 로컬 송금은 `송금중`에서 `성공`으로 전이한다.
- 중앙 결제 거절을 확인하고 출금을 보상하면 로컬 송금은 `송금중`에서 `실패`로 전이한다.
- 수취 은행이 수취 가능을 확인하고 결제잔액이 충분하면 중앙 거래는 `수취검증대기`에서 `결제완료`로 전이한다.
- 수취 불가가 확정되거나 송금 은행의 결제잔액이 부족하면 중앙 거래는 `수취검증대기`에서 `결제거절`로 전이한다.

### 선택 이유

- 독립적인 고객 송금 동작과 양쪽 은행의 거래 기록으로 MVP의 시작과 관찰 가능한 결과를 명확히 할 수 있다.
- 실제 입금 기능 없이도 계좌 생성 시 테스트 자금으로 송금 시연을 시작할 수 있다.
- 같은 은행 송금은 의미 있는 기능이지만 중앙 결제와 분산된 로컬 반영 문제를 실험하려는 프로젝트 목적에는 필수적이지 않다.
- 최소 상태만 먼저 두어 2주차 구현 복잡도를 제한하면서 이후 timeout, 중복, 동시성과 부분 실패 실험에 필요한 경계는 남긴다.
- 결제잔액 부족을 도메인 규칙으로 보존하면 중앙 원장의 불변식을 유지할 수 있고, 복잡한 유동성 관리는 제외할 수 있다.

### 파생 불변식

- 송금액은 0보다 큰 정수여야 한다.
- 고객 계좌와 은행 결제계좌는 송금으로 인해 음수 잔액이 되어서는 안 된다.
- 테스트 자금 지급, 송금 출금과 수취 입금은 대응하는 거래 기록과 잔액 갱신을 하나의 로컬 DB 트랜잭션으로 처리해야 한다.
- 중앙 결제의 `결제완료`와 `결제거절`, 로컬 송금의 `성공`과 `실패`는 서로 뒤바뀌지 않는 최종 상태여야 한다.

### 보류 사항

- 계좌 개설 시 지급할 테스트 자금을 환경별로 설정하는 방식

## D-024 — 송금 시작 전 요청 거절과 시작 후 실패의 구분

> 현재 상태: 유지. 사전 검증 거절의 기록 여부와 로컬 송금 `실패`의 의미를 정의한다.

### 결정

- 송금액 형식과 고객 계좌 잔액은 송금 거래 생성과 출금 전에 검증한다.
- 송금액이 유효하지 않거나 고객 잔액이 부족하면 요청을 즉시 거절한다.
- 이 사전 검증에서 거절된 요청은 송금 거래나 계좌 거래 기록으로 생성하지 않는다.
- 로컬 송금의 `실패`는 출금되어 `송금중`에 진입한 뒤 중앙 결제가 거절되고 출금 보상까지 완료된 경우에만 사용한다.
- 사전 거절 시도의 별도 감사 로그나 요청 이력은 현재 MVP에서 다루지 않는다.

### 선택 이유

- 사전 검증 거절에서는 돈이 이동하지 않으므로 잔액 변동을 설명하는 계좌 거래 기록의 대상이 아니다.
- 요청 거절과 시작된 송금의 실패를 분리하면 `실패`가 출금과 보상을 수반하는 하나의 의미를 가진다.
- 사전 거절까지 실패 송금으로 저장하면 실패 단계, 출금 여부와 보상 여부를 추가로 구분해야 하므로 현재 MVP의 데이터 모델이 불필요하게 복잡해진다.
- 추후 감사 요구가 생기면 계좌 거래 내역과 분리된 요청 로그로 확장할 수 있다.

### 파생 불변식

- 사전 검증에 실패한 요청은 고객 잔액과 계좌 거래 기록을 변경해서는 안 된다.
- `실패` 상태인 로컬 송금에는 원래 출금 기록과 그 출금을 반환한 보상 기록이 각각 한 번씩 존재해야 한다.
- `송금중`에 진입하지 않은 요청을 `실패` 송금으로 기록해서는 안 된다.

## D-025 — 계좌 생성 시 테스트 초기 자금

> 현재 상태: 대체. 새 계좌에 잔액과 `초기 자금` 기록을 직접 생성하는 방식은 D-030의 은행 내부 이체 방식으로 대체했다.

### 결정

- 계좌를 생성하면 테스트 자금 100,000원을 자동 지급한다.
- 현재 잔액 증가와 초기 자금 거래 기록 생성은 하나의 로컬 DB 트랜잭션으로 처리한다.
- 초기 자금은 실제 외부 입금이 아니라 시연용 데이터임을 거래 기록에서 구분할 수 있어야 한다.

### 선택 이유

- 100,000원은 송금 전후 잔액을 사람이 쉽게 계산하면서 여러 송금 사례를 시연하기에 충분하다.
- 초기 자금에도 거래 기록을 남겨 현재 잔액을 모든 금액 변동 기록으로 설명한다는 불변식을 유지한다.
- 실제 금융망이나 별도의 고객 입금 기능을 추가하지 않고도 최소 송금 흐름을 시작할 수 있다.

### 파생 불변식

- 새 계좌의 최초 잔액은 100,000원이어야 한다.
- 새 계좌에는 100,000원의 초기 자금 거래 기록이 정확히 하나 존재해야 한다.
- 초기 자금 거래 기록 없이 계좌 잔액만 증가해서는 안 된다.

## D-026 — 송금과 결제 용어 구분

> 현재 상태: 유지. 고객 업무와 중앙 시스템의 은행 간 자금 처리를 구분한다.

### 결정

- 고객이 요청하는 전체 업무는 `송금`으로 표현한다.
- 중앙 결제 시스템이 은행별 결제잔액을 이동하고 은행 간 자금 이동 결과를 확정하는 처리는 `결제`로 표현한다.
- 중앙 결제 거래의 최종 상태는 `결제완료`와 `결제거절`로 유지한다.
- 각 은행의 고객 계좌 변동은 `출금`과 `입금`으로 표현한다.
- `거래`는 송금, 중앙 결제 기록, 계좌 거래 기록을 문맥에 따라 가리키는 일반 용어로만 사용하고, 중앙 상태명으로 `거래완료`를 사용하지 않는다.

### 선택 이유

- `결제`는 이 프로젝트에서 중앙 시스템이 권위 있게 확정하는 은행 간 결제잔액 이동을 구체적으로 드러낸다.
- `거래완료`는 중앙 결제만 끝난 상태인지, 수취 은행의 고객 계좌 입금까지 모두 끝난 상태인지 구분하기 어렵다.
- 송금·결제·출금·입금을 구분하면 중앙 결제는 완료됐지만 개별 은행의 로컬 반영은 지연될 수 있는 이 프로젝트의 핵심 부분 실패를 명확히 설명할 수 있다.

## D-027 — 결제 결과 전달과 로컬 반영의 분리

> 현재 상태: 유지. MVP는 polling을 사용하되 로컬 반영 규칙을 통신 방식에 결합하지 않는다.

### 결정

- MVP에서 송금 은행과 수취 은행은 중앙 결제 결과를 polling으로 조회한다.
- polling은 중앙 결제 기록을 가져오는 책임만 가진다.
- 가져온 결제 결과를 로컬 송금 상태, 계좌 잔액과 거래 기록에 반영하는 규칙은 polling 책임과 분리한다.
- 로컬 반영 규칙은 결제 결과가 polling으로 조회됐는지, push로 통지됐는지에 의존하지 않는다.
- push 통지는 현재 MVP 구현 범위에 포함하지 않는다.

### 선택 이유

- polling 코드에 계좌 입금과 송금 상태 변경을 직접 결합하면, 전달 방식을 push로 변경할 때 도메인 반영 로직까지 다시 작성해야 한다.
- 두 책임을 분리하면 계좌, 거래 기록, 외부 거래 ID와 멱등성 모델을 유지한 채 결과 수신 방식만 변경할 수 있다.
- polling과 로컬 반영을 독립적으로 구현·테스트할 수 있어 장애 원인과 책임 경계가 명확해진다.

### 범위 제한

- 이 결정은 push를 미리 구현하거나 push 전용 상태를 도메인 모델에 추가하라는 의미가 아니다.
- polling 주기, 한 번에 조회할 건수, 마지막 조회 위치와 다중 Pod 경쟁 처리는 기존 미정 사항으로 남긴다.

## D-028 — 송금과 계좌 거래 기록의 분리

> 현재 상태: 유지. 송금의 진행 상태와 잔액 변동의 근거를 서로 다른 모델로 관리한다.

### 결정

- `송금`과 `계좌 거래 기록`을 분리한다.
- 송금은 외부 거래 ID, 송금 내용과 `송금중`·`성공`·`실패` 상태를 관리한다.
- 계좌 거래 기록은 계좌 잔액에 반영된 개별 금액 변동의 근거를 관리한다.
- 하나의 송금은 여러 계좌 거래 기록과 연결될 수 있다.
- 계좌 거래 기록은 은행 내부 이체 출금·입금, 송금 출금, 수취 입금과 거절 보상을 구분하는 반영 종류를 가진다.
- 송금과 관련된 계좌 거래 기록의 멱등성 단위는 `(외부 거래 ID, 반영 종류)`다.

### 선택 이유

- 송금 하나에서 출금과 보상처럼 서로 다른 잔액 변동이 정당하게 한 번씩 발생할 수 있다.
- 송금 상태를 변경해도 이미 발생한 출금·입금·보상 기록을 덮어쓰거나 잃지 않아야 한다.
- 외부 거래 ID만을 멱등성 기준으로 삼으면 출금 후의 정당한 보상을 중복으로 잘못 판단할 수 있다.
- 반영 종류를 함께 사용하면 출금과 보상을 각각 한 번씩 허용하면서 같은 종류의 중복 반영은 막을 수 있다.

## D-029 — 계좌 거래 기록의 부호 있는 금액

> 현재 상태: 유지. 운영 중 기록에서 잔액 증감 방향을 직접 확인할 수 있게 한다.

### 결정

- 계좌 거래 기록의 금액은 잔액 변동량으로 저장한다.
- 출금은 음수, 입금과 보상은 양수로 저장한다.
- 0원의 계좌 거래 기록은 허용하지 않는다.
- 반영 종류와 금액 부호가 모순되는 기록은 허용하지 않는다.

### 선택 이유

- 운영자가 기록을 보고 계좌 잔액이 증가했는지 감소했는지 직접 판단할 수 있다.
- 일정 구간의 잔액 변동량을 부호 있는 금액의 합으로 계산할 수 있다.
- 반영 종류는 멱등성과 업무 의미를, 금액 부호는 잔액 증감 방향을 표현한다.

## D-030 — 계좌 생성 시 은행 자금 계좌의 내부 이체

> 현재 상태: 일부 대체. `초기 자금` 기록 대신 실제 계좌 간 금액 변동으로 설명한다는 결정은 유지하고, 은행 자금 계좌를 별도 도메인 개념으로 두는 부분은 D-031로 대체했다.

### 결정

- 각 은행은 계좌 생성 시 자금을 보낼 특정 은행 자금 계좌를 둔다.
- 고객 계좌를 생성하면 은행 자금 계좌에서 새 고객 계좌로 100,000원을 내부 이체한다.
- 은행 자금 계좌의 출금과 새 고객 계좌의 입금을 각각 계좌 거래 기록으로 남긴다.
- `초기 자금`이라는 반영 종류나 계좌 거래 기록은 사용하지 않는다.
- 이 내부 이체는 계좌 생성 시에만 사용하며 일반 고객용 동일 은행 송금 기능은 MVP에서 계속 제외한다.
- 일반 고객은 은행 자금 계좌를 조회하거나 거래에 사용할 수 없다.

### 선택 이유

- 새 고객 계좌의 100,000원을 출처 없는 잔액으로 직접 설정하지 않고, 어느 계좌에서 이체됐는지 기록으로 설명할 수 있다.
- 일반 동일 은행 송금 기능을 공개하지 않아 MVP 범위를 제한한다.

### 미정 사항

- 은행 자금 계좌와 고객 계좌를 같은 저장 모델로 관리할지 여부
- 은행 자금 계좌의 최초 잔액을 설정하는 방식
- 계좌 생성, 은행 자금 계좌 출금, 고객 계좌 입금과 양쪽 거래 기록의 정확한 트랜잭션 경계

## D-031 — 시연용 고객 계좌를 통한 계좌 생성 자금 지급

> 현재 상태: 유지. D-030의 은행 자금 계좌를 시연용 고객이 소유한 일반 계좌로 대체한다.

### 결정

- 모든 계좌는 정확히 한 고객이 소유하며 고객 식별자는 필수다.
- 시연용 자금 공급 계좌에도 별도 계좌 유형을 두지 않는다.
- 개발·시연 환경의 초기 데이터로 시연용 고객과 그 고객이 소유한 계좌를 준비한다.
- 고객 계좌를 생성하면 시연용 고객 계좌에서 새 고객 계좌로 100,000원을 내부 이체한다.
- 시연용 계좌의 출금과 새 고객 계좌의 입금을 각각 계좌 거래 기록으로 남긴다.
- 이 내부 이체는 계좌 생성 과정에서만 실행하며 일반 고객용 동일 은행 송금 기능은 MVP에서 제공하지 않는다.

### 선택 이유

- 모의 데이터를 제공하기 위한 편의 때문에 실제 계좌 도메인에 `은행 자금 계좌` 같은 유형을 추가하지 않는다.
- 모든 계좌의 소유 관계와 고객 식별자 필수 규칙을 예외 없이 유지한다.
- 새 고객 계좌의 100,000원은 출처 없는 잔액이나 `초기 자금` 기록이 아니라 실제 두 계좌의 거래 기록으로 설명한다.

### 대체한 대안

- 은행 자금 계좌 유형 추가: 시연용 데이터 때문에 운영 도메인과 조회 권한 규칙이 복잡해지므로 선택하지 않았다.
- 고객 식별자가 없는 계좌 허용: 누락된 소유 관계와 비고객 계좌를 구분할 수 없고, 모든 계좌가 고객 소유라는 규칙을 약화하므로 선택하지 않았다.
- 출발 계좌 없이 잔액 직접 주입: 자금 출처와 잔액 변동 기록을 일치시킬 수 없으므로 선택하지 않았다.

### 미정 사항

- 시연용 고객 계좌와 은행 결제계좌의 최초 잔액을 준비하는 방식
- 계좌 생성, 시연용 계좌 출금, 신규 계좌 입금과 양쪽 거래 기록의 정확한 트랜잭션 경계

## D-032 — 내부 계좌 식별자와 계좌번호 분리

> 현재 상태: 유지. 내부 식별자와 외부에서 사용하는 계좌번호를 서로 다른 속성으로 관리한다.

### 결정

- `Account.id`는 은행 시스템 내부에서 사용하는 계좌 식별자다.
- `Account.account_number`는 고객과 은행 간 송금에서 사용하는 계좌번호다.

### 선택 이유

- 데이터베이스 내부 관계에 사용하는 식별자와 외부에 노출되는 금융 도메인 식별자의 역할을 분리한다.
- 내부 식별자 표현이 바뀌어도 고객에게 제공한 계좌번호의 의미가 영향을 받지 않게 한다.

### 미정 사항

- 계좌번호의 생성 방식
- 계좌번호의 자료형과 길이
- 계좌번호의 구체적인 유일성 제약

## D-033 — 고객 모델에 최소 로그인 정보 저장

> 현재 상태: 유지. MVP 회원가입과 로그인에 필요한 최소 인증 정보를 고객 모델에 둔다.

### 결정

- `Customer.login_id`는 회원가입과 로그인에 사용하는 식별자다.
- `login_id`는 한 은행 시스템 안에서 고유하며 반드시 존재해야 한다.
- `Customer.password_hash`에는 단방향 해시된 비밀번호만 저장한다.
- 평문 비밀번호는 저장하지 않는다.
- MVP에서는 로그인 정보를 별도 인증 모델로 분리하지 않는다.

### 선택 이유

- 회원가입과 로그인이라는 합의된 기능을 구현할 수 있는 최소 정보를 갖춘다.
- 현재 범위에는 여러 인증 수단이나 인증 정보의 독립적인 생명주기가 없으므로 별도 모델을 만들지 않는다.
- 로그인 식별자의 중복을 막아 하나의 로그인 요청이 하나의 고객으로 결정되게 한다.

## D-034 — MVP 고객 이름 제외

> 현재 상태: 유지. 고객 모델에 별도 이름을 저장하지 않고 `login_id`로 고객을 식별한다.

### 결정

- `Customer.name`은 MVP 데이터 모델에 포함하지 않는다.
- 고객의 로그인과 화면상 식별에는 `login_id`를 사용한다.
- `Account.name`의 포함 여부는 이 결정과 별개이며 아직 미정이다.

### 선택 이유

- KYC와 실명 확인은 프로젝트 범위 밖이다.
- 송금 신뢰성 실험에는 별도의 고객 이름이 필요하지 않으므로 MVP 모델을 단순하게 유지한다.

## D-035 — 계좌 거래 기록의 필드와 자금 이동 식별자

> 현재 상태: 일부 대체. 필드 구성과 공유 식별자 규칙은 유지하고, `transfer_id`라는 이름은 D-038의 `transfer_key`로 대체했다.

### 결정

- 계좌 거래 기록은 `id`, `account_id`, `transfer_id`, `other_bank_code`, `other_account_number`, `amount`, `type`, `created_at`을 가진다.
- `label`은 MVP에서 제외한다.
- `transfer_id`는 DB 트랜잭션 ID가 아니라 하나의 자금 이동을 식별하는 값이다.
- 동일한 자금 이동을 재시도하거나 다시 조회해도 `transfer_id`는 유지한다.
- 은행 간 송금에서는 송금 은행, 중앙 결제 시스템과 수취 은행이 같은 `transfer_id`를 사용한다.
- 내부 이체에도 하나의 `transfer_id`를 발급해 출금과 입금 기록을 연결한다.
- `other_bank_code`는 내부 이체에서도 생략하지 않고 현재 은행 코드를 기록한다.
- 한 은행 DB에서 `(transfer_id, type)` 조합은 고유해야 한다.
- 계좌 거래 기록은 생성 후 수정하거나 삭제하지 않는다.

### 선택 이유

- 계좌 잔액 변동이 어떤 자금 이동에서 발생했는지 중앙 결제 기록까지 추적할 수 있다.
- `transfer_id`와 `type`을 함께 사용하면 같은 송금의 출금과 보상은 각각 허용하면서 동일 반영의 중복은 막을 수 있다.
- 상대 은행과 계좌번호를 기록하면 다른 시스템의 DB를 읽지 않고도 거래 상대를 확인할 수 있다.
- `label`은 반영 종류와 상대 정보로 표현할 수 있고 현재 요구사항에 별도 메모 기능이 없으므로 제외한다.

## D-036 — 송금 상태와 계좌 거래 기록의 생성 시점 분리

> 현재 상태: 유지. 계좌 거래 기록은 송금의 최종 완료가 아니라 실제 잔액 변경 시점에 생성한다.

### 결정

- `Transfer`는 송금 요청의 `송금중`·`성공`·`실패` 진행 상태를 표현한다.
- `AccountTransaction`은 특정 계좌에 실제 반영된 잔액 변화를 표현한다.
- 송금을 시작하며 선출금하면 `Transfer`가 `송금중`이어도 출금 거래 기록을 생성한다.
- 중앙 결제가 거절되어 출금액을 반환하면 별도의 보상 거래 기록을 생성한다.
- 수취 은행은 완료된 중앙 결제를 고객 계좌 잔액에 반영할 때 입금 거래 기록을 생성한다.
- 잔액 변경과 대응하는 계좌 거래 기록 생성은 하나의 로컬 DB 트랜잭션으로 처리한다.

### 선택 이유

- 최종 완료 시점에만 거래 기록을 만들면 `송금중` 동안 이미 감소한 계좌 잔액을 거래 기록으로 설명할 수 없다.
- 송금 워크플로 상태와 실제 금액 반영 사실을 분리하면 부분 실패 상황에서도 현재 잔액의 근거를 유지할 수 있다.

## D-037 — 내부 송금 ID와 공유 송금 식별자 분리

> 현재 상태: 일부 대체. 내부 PK와 공유 키의 분리는 유지하고, 공유 필드 이름 `transfer_id`는 D-038의 `transfer_key`로 대체했다.

### 결정

- `Transfer.id`는 송금 은행 DB 내부에서 사용하는 PK다.
- `Transfer.transfer_id`는 송금 은행과 중앙 결제 시스템이 공유하는 업무 식별자다.
- 동일한 중앙 결제 요청을 재시도해도 `transfer_id`는 유지한다.
- `transfer_id`는 송금 은행 안에서 고유하며 생성 후 변경하지 않는다.
- `AccountTransaction.transfer_id`는 같은 값을 저장하여 송금과 잔액 변경 기록을 연결한다.
- 고객이 송금 은행에 보내는 요청의 별도 `idempotency_key`는 현재 데이터 모델에 포함하지 않고 5주차 중복 요청 실험에서 검토한다.

### 선택 이유

- 내부 저장 관계에 사용하는 PK와 독립 시스템 사이에서 공유하는 업무 식별자의 역할을 구분한다.
- 요청이나 응답이 유실되어 중앙 결제를 재요청해도 동일한 송금으로 판별하여 중복 결제를 막을 수 있다.
- 아직 설계하지 않은 고객 요청 멱등성까지 미리 모델에 추가하지 않아 1주차 범위를 유지한다.

## D-038 — 시스템 간 공유 송금 키 이름

> 현재 상태: 유지. 시스템 간에 공유하는 송금 식별자의 필드 이름을 `transfer_key`로 사용한다.

### 결정

- `Transfer.id`는 송금 은행 DB의 auto increment PK다.
- `Transfer.transfer_key`는 송금 은행과 중앙 결제 시스템이 공유하는 송금 키다.
- `AccountTransaction.transfer_key`와 중앙 결제 거래의 `transfer_key`도 같은 값을 사용한다.
- `transfer_key`는 고유하고 반드시 존재하며 생성 후 변경하지 않는다.
- 재시도와 polling에서도 최초 `transfer_key`를 유지한다.
- 계좌 거래 기록의 멱등성 제약은 `(transfer_key, type)` 조합으로 표현한다.

### 선택 이유

- auto increment인 로컬 `id`는 독립된 여러 DB에서 충돌할 수 있으므로 시스템 간 공유 식별자로 사용할 수 없다.
- `transfer_key`는 `Transfer.transfer_id`의 이름 반복을 줄이면서 송금에 관한 공유 키라는 의미를 드러낸다.
- `global_id`나 `external_id`보다 키의 대상과 역할이 명확하다.

## D-039 — 계좌 이름 유지

> 현재 상태: 유지. `Account.name`을 MVP 데이터 모델에서 제거하지 않는다.

### 결정

- `Account.name` 필드를 유지한다.
- 필수 여부와 변경 가능 여부는 아직 확정하지 않는다.

### 선택 이유

- 고객 이름과 달리 계좌 이름은 여러 계좌를 구분하는 별칭으로 사용할 수 있으므로 현재 모델에 남긴다.

## D-040 — 참가 은행과 결제잔액 통합 모델

> 현재 상태: 일부 대체. 별도 결제계좌 모델 없이 참가 은행에 결제잔액을 저장하는 구조는 유지하고, 모델 이름은 D-041의 `Bank`로 대체했다.

### 결정

- 중앙 결제 시스템의 참가 은행 모델 이름은 `SettlementParticipant`로 사용한다.
- `SettlementParticipant`는 `id`, `bank_code`, `balance`, `created_at`, `updated_at`을 가진다.
- `id`는 중앙 결제 DB의 auto increment PK다.
- `bank_code`는 은행과 중앙 결제 시스템이 공유하는 고유한 은행 식별자다.
- 참가 은행마다 원화 결제잔액 하나만 관리한다.
- 별도의 `SettlementAccount` 모델을 만들지 않고 `SettlementParticipant.balance`에 현재 결제잔액을 저장한다.
- 결제 처리로 인해 참가 은행의 결제잔액이 음수가 되어서는 안 된다.

### 선택 이유

- 현재 범위에는 한 은행당 결제잔액이 하나이며 통화도 원화 하나뿐이다.
- 결제계좌의 독립적인 생성·해지·상태나 다중 계좌 요구사항이 없어 1:1 모델 분리는 불필요하다.
- 별도 결제계좌 모델 없이도 중앙 결제 거래로 잔액 변동을 설명하고 결제잔액의 정합성과 동시성을 실험할 수 있다.

### 확장 시 재검토 조건

- 한 참가자가 여러 결제계좌를 가져야 하는 경우
- 통화별 결제잔액을 관리하는 경우
- 준비금·결제·선불 계좌처럼 서로 다른 계좌 종류가 필요한 경우
- 결제계좌 자체의 상태나 생명주기를 관리하는 경우

## D-041 — 중앙 결제 참가 은행 모델 이름

> 현재 상태: 유지. 중앙 결제 시스템의 참가 은행 모델 이름을 `Bank`로 사용한다.

### 결정

- 기존 후보였던 `SettlementParticipant` 대신 `Bank`를 사용한다.
- 중앙 결제 시스템의 `Bank`는 시스템에 참가하는 은행과 그 은행의 현재 결제잔액을 나타낸다.
- 별도의 `SettlementAccount` 모델은 만들지 않고 `Bank.balance`에 현재 결제잔액을 저장한다.

### 선택 이유

- MVP의 참가자는 은행으로만 한정되어 있어 더 일반적인 `SettlementParticipant`라는 이름이 필요하지 않다.
- 중앙 결제 시스템이라는 경계 안에서는 `Bank`만으로 모델의 대상이 충분히 명확하다.

## D-042 — 중앙 결제 상태의 소유와 의미

> 현재 상태: 일부 대체. 상태 소유와 전이 규칙은 유지하고, `RECEIVER_VALIDATION_PENDING` 이름은 D-044의 `RECIPIENT_VALIDATION_PENDING`으로 대체했다.

### 결정

- `SettlementTransfer.status`는 `RECEIVER_VALIDATION_PENDING`, `SETTLED`, `REJECTED` 중 하나다.
- 최초 상태는 `RECEIVER_VALIDATION_PENDING`이다.
- 수취 은행의 수취 가능 확인 후 `SETTLED`, 수취 불가 확인 후 `REJECTED`로 전이한다.
- `SETTLED`와 `REJECTED`는 되돌리거나 서로 변경할 수 없는 최종 상태다.
- `SETTLED`는 은행 간 결제잔액 이동 완료를 의미하며 수취 고객 계좌 입금 완료를 의미하지 않는다.
- `SETTLED` 전이와 두 `Bank.balance`의 차감·증가는 하나의 중앙 DB 트랜잭션으로 처리한다.
- `REJECTED` 확정 시 두 은행의 결제잔액은 변경하지 않는다.

### 선택 이유

- 중앙 결제 시스템이 은행 간 결제 결과의 권위 있는 주체이므로 결제 상태도 중앙 결제 거래가 소유해야 한다.
- 은행의 로컬 송금 상태와 중앙 결제 상태를 분리하여 결제완료 후 고객 계좌 반영이 지연되는 상황을 표현한다.
- 상태 확정과 결제잔액 변경을 원자적으로 처리하여 `SETTLED`가 실제 은행 간 잔액 이동을 보장하게 한다.

## D-043 — 중앙 결제 거래 필드와 방향 용어 통일

> 현재 상태: 유지. 중앙 결제 거래의 최소 필드와 프로젝트 전체의 송금 방향 용어를 확정한다.

### 결정

- `SettlementTransfer`는 `id`, `transfer_key`, `source_bank_id`, `source_account_number`, `recipient_bank_id`, `recipient_account_number`, `amount`, `status`, `created_at`, `updated_at`을 가진다.
- `id`는 중앙 결제 DB의 auto increment PK다.
- `transfer_key`는 고유하고 반드시 존재하며 생성 후 변경하지 않는다.
- `source_bank_id`와 `recipient_bank_id`는 각각 중앙 결제 DB의 `Bank.id`를 참조하며 서로 달라야 한다.
- 고객 계좌번호는 거래 식별과 수취 검증을 위한 참조 정보이며 중앙 결제 시스템이 고객 계좌나 잔액을 소유한다는 의미가 아니다.
- 자금이 나가는 쪽은 `source_*`, 받는 쪽은 `recipient_*`로 표현한다.
- 같은 의미로 `sender_*`, `receiver_*`, `destination_*`, `target_*`를 섞어 쓰지 않는다.
- 계좌 거래 기록에서 상대편은 기존 결정대로 `other_*`로 표현한다.

### 선택 이유

- 은행의 `Transfer`와 중앙의 `SettlementTransfer`가 동일한 송금 방향 용어를 사용하면 모델 사이의 대응 관계를 바로 이해할 수 있다.
- 중앙 결제 거래에 양쪽 은행과 고객 계좌번호를 저장해야 동일 키의 내용 충돌을 판별하고 수취 은행에 검증 대상을 전달할 수 있다.
- 중앙 DB 내부 관계에는 외부 은행 코드 대신 `Bank.id`를 사용하고, 외부 요청에서 받은 은행 코드는 `Bank` 조회에 사용한다.

## D-044 — 수취 검증 대기 상태의 영문 이름 통일

> 현재 상태: 유지. 중앙 결제의 수취 검증 대기 상태를 `RECIPIENT_VALIDATION_PENDING`으로 표현한다.

### 결정

- 기존 `RECEIVER_VALIDATION_PENDING`을 `RECIPIENT_VALIDATION_PENDING`으로 변경한다.
- `SettlementTransfer.status`는 `RECIPIENT_VALIDATION_PENDING`, `SETTLED`, `REJECTED` 중 하나다.
- 도메인 용어 `수취검증대기`, `결제완료`, `결제거절`은 각각 위 세 영문 상태에 대응한다.

### 선택 이유

- 프로젝트에서 돈을 받는 쪽은 `recipient_*`로 표현하기로 했으므로 상태 이름에도 같은 용어를 사용한다.
- 동일 개념에 `receiver`와 `recipient`를 혼용할 때 생기는 모델 해석 비용을 줄인다.

## D-045 — 계좌 거래 기록의 반영 종류

> 현재 상태: 유지. `AccountTransaction.type`은 출금, 입금과 보상을 구분하는 세 값만 사용한다.

### 결정

- `AccountTransaction.type`은 `DEBIT`, `CREDIT`, `COMPENSATION` 중 하나다.
- `DEBIT`의 `amount`는 음수다.
- `CREDIT`과 `COMPENSATION`의 `amount`는 양수다.
- 시연용 내부 이체는 출발 계좌에 `DEBIT`, 신규 계좌에 `CREDIT`으로 기록한다.
- 은행 간 송금은 송금 계좌에 `DEBIT`, 수취 계좌에 `CREDIT`으로 기록한다.
- 중앙 결제거절에 따른 출금 반환은 `COMPENSATION`으로 기록한다.

### 선택 이유

- 현재 MVP에서 발생하는 모든 계좌 잔액 변동을 세 종류로 표현할 수 있다.
- 보상은 금액 방향만 보면 입금이지만 정상 수취 입금과 업무 의미가 다르므로 `CREDIT`과 구분한다.
- `(transfer_key, type)` 고유 제약으로 동일 송금의 출금과 보상은 각각 한 번 허용하면서 같은 반영의 중복은 막는다.
- 수수료, 지급 보류, 관리자 조정, 현금 입출금과 거래 취소는 현재 범위 밖이므로 유형을 미리 추가하지 않는다.

## D-046 — UUID 계좌번호

> 현재 상태: 유지. 신규 계좌의 `account_number`는 임의의 UUID로 발급한다.

### 결정

- 계좌를 생성할 때 임의의 UUID를 `Account.account_number`로 발급한다.
- `account_number`는 은행 DB 안에서 고유하고 반드시 존재해야 한다.
- UUID 충돌 가능성과 무관하게 DB 고유 제약을 둔다.
- 한 번 발급한 계좌번호는 변경하지 않는다.
- 은행 간에는 `bank_code`와 `account_number`의 조합으로 계좌를 지정한다.

### 선택 이유

- 실제 은행식 계좌번호 발급 규칙을 설계하는 것은 거래 정합성을 실험하는 프로젝트 목적과 직접 관련이 없다.
- UUID를 사용하면 두 은행이 독립적으로 계좌번호를 생성해도 충돌 가능성이 매우 낮고 별도 번호 발급기를 구현하지 않아도 된다.
- DB 고유 제약을 함께 사용하여 충돌이 발생해도 중복 계좌번호가 저장되지 않게 한다.

### 감수한 단점

- 실제 은행 계좌번호처럼 읽거나 입력하기 편한 형식은 아니다.
- MVP와 시연에서는 단순성을 우선하며, 사용자 친화적인 번호 형식은 범위에 포함하지 않는다.

## D-047 — 식별자와 생성 시각 매핑 공통화

> 현재 상태: 유지. 은행 JPA 엔티티의 공통 매핑을 `IdCreatedAtEntity`에 둔다.

### 결정

- `Customer`, `Account`, `AccountTransaction`처럼 동일한 식별자와 생성 시각 매핑을 사용하는 엔티티는 `IdCreatedAtEntity`를 상속한다.
- `IdCreatedAtEntity`는 `@MappedSuperclass`로 선언하고 auto increment `id`와 `created_at` 매핑을 제공한다.
- 이 상속은 도메인 타입의 다형성을 표현하지 않고 JPA 매핑을 재사용하기 위한 구현 선택이다.
- 공통 클래스에 엔티티 종류를 넘는 업무 상태나 업무 행위를 추가하지 않는다.

### 선택 이유

- 각 엔티티에 동일한 식별자와 Auditing 코드를 반복 작성하는 비용을 줄여 구현 생산성을 높인다.
- 상속은 타입 다형성만을 위한 수단은 아니며, 현재의 작고 통제된 JPA 매핑 계층에서는 감수할 수 있는 결합이라고 판단했다.

### 감수한 단점

- 개별 엔티티 파일만 읽으면 상속된 컬럼이 바로 보이지 않는다.
- 모든 하위 엔티티가 같은 식별자 전략에 결합된다.
- 도메인 상속으로 오해되지 않도록 공통 클래스의 책임을 식별자와 생성 시각 매핑으로 제한해야 한다.

## D-048 — 계좌번호 생성 책임

> 현재 상태: 유지. 계좌번호 UUID는 엔티티가 아니라 서비스의 생성기가 발급한다.

### 결정

- 계좌 생성 서비스는 계좌번호 생성기를 사용해 UUID 계좌번호를 발급한다.
- 생성된 계좌번호를 `Account.create`에 전달한다.
- `Account` 엔티티는 전달받은 계좌번호를 필수·고유·변경 불가 값으로 보관한다.
- DB 고유 제약은 UUID 생성 위치와 관계없이 유지한다.

### 선택 이유

- 무작위 값 생성 책임을 엔티티 생성과 분리하면 테스트에서 계좌번호를 통제할 수 있다.
- 생성 정책이 바뀌더라도 `Account`의 상태와 불변식에 미치는 영향을 줄일 수 있다.
- 서비스가 계좌 생성 절차를 조정하고 엔티티는 전달받은 계좌번호를 보관하는 책임에 집중한다.

## D-049 — Flyway와 JPA 스키마 메타데이터의 역할

> 현재 상태: 유지. Flyway가 DDL을 실행하고, 엔티티는 이름 있는 고유 제약과 인덱스를 현재 스키마의 발견 가능한 표현으로 함께 기록한다.

### 결정

- 실제 DB 스키마 생성과 변경은 Flyway 마이그레이션만 수행한다.
- 개발자가 엔티티를 읽으면서 고유 제약과 인덱스를 발견하고 쿼리 설계에 참고할 수 있도록 JPA 메타데이터에도 이를 기록한다.
- 엔티티와 Flyway에서는 제약 이름, 대상 컬럼과 컬럼 순서를 동일하게 사용한다.
- 단일 컬럼 고유 제약도 이름을 명시할 수 없는 `@Column(unique = true)` 대신 `@Table`의 `UniqueConstraint`로 표현한다.
- Hibernate의 스키마 검증은 명시적으로 이름 붙인 인덱스와 고유키도 검사하도록 설정한다.
- 스키마 변경 시 Flyway와 대응하는 엔티티 메타데이터를 같은 변경 단위에서 함께 수정한다.
- 별도의 스키마 계약 테스트는 만들지 않는다.

### 선택 이유

- Flyway 마이그레이션은 변경 이력을 잘 보여주지만, 파일이 누적되면 개발자가 현재 제약과 인덱스를 한눈에 파악하기 어렵다.
- 고유 제약과 인덱스는 쿼리의 정확성과 성능 판단에 필요하므로 엔티티 가까이에서도 확인할 수 있어야 한다.
- 이름 있는 제약을 양쪽에 기록하고 Hibernate의 내장 검증을 사용하면 별도의 비교 테스트를 만들지 않고도 주요 불일치를 애플리케이션 시작 시 발견할 수 있다.
- 현재 프로젝트 규모에서는 별도의 스키마 모델이나 범용 계약 테스트를 유지하는 비용이 더 크다.

### 감수한 한계

- 엔티티와 Flyway에 같은 정보를 중복 기록하므로 변경 시 두 곳을 함께 수정해야 한다.
- Hibernate의 인덱스·고유키 검증은 외래키, `CHECK`, 트리거와 DB 전용 인덱스 옵션까지 모두 검증하지 않는다.
- Hibernate 버전에 의존하는 검증 설정이므로 프레임워크 버전을 변경할 때 지원 여부와 동작을 다시 확인해야 한다.

## D-050 — 은행 내부 참조의 외래키와 인덱스 표현

> 현재 상태: 유지. 외래키 제약은 Flyway에 두고, 외래키 컬럼의 인덱스는 Flyway와 JPA 엔티티 양쪽에 기록한다.

### 결정

- `accounts.customer_id`는 `customers.id`를 참조하는 외래키로 제한한다.
- `account_transactions.account_id`는 `accounts.id`를 참조하는 외래키로 제한한다.
- 두 외래키에는 삭제 전파를 설정하지 않는다.
- 외래키 제약은 Flyway에서만 선언한다.
- `customer_id`와 `account_id`의 이름 있는 인덱스는 Flyway와 각 엔티티의 `@Table(indexes = ...)`에 함께 기록한다.
- 외래키를 엔티티에 표시하기 위한 JPA 연관관계는 도입하지 않고 기존의 식별자 프로퍼티를 유지한다.

### 선택 이유

- 외래키는 존재하지 않는 고객이나 계좌를 참조하는 거래가 저장되지 않도록 DB 수준에서 정합성을 보장한다.
- 외래키 컬럼은 고객별 계좌와 계좌별 거래 내역 조회에 사용되므로 명시적인 인덱스를 둔다.
- 인덱스를 엔티티에도 기록하면 개발자가 현재 조회 조건과 성능 구조를 가까운 코드에서 파악할 수 있다.
- 외래키를 표현하려는 목적으로만 JPA 연관관계를 도입하면 프록시와 로딩 정책 등 현재 필요하지 않은 복잡성이 생긴다.

### 감수한 한계

- 엔티티만 읽어서는 외래키 제약의 존재와 참조 대상을 완전히 확인할 수 없으므로 Flyway를 함께 확인해야 한다.
- 인덱스 정보는 Flyway와 엔티티에 중복되므로 스키마 변경 시 두 곳을 함께 수정해야 한다.

## D-051 — Hibernate Envers를 사용하지 않는다

> 현재 상태: 유지. 엔티티 변경 이력용 Envers 테이블을 은행 스키마에 만들지 않는다.

### 결정

- Hibernate Envers와 `@Audited`를 도입하지 않는다.
- Flyway V1에서 `revinfo`, `revchanges` 테이블과 두 테이블 사이의 외래키를 제거한다.
- 생성·수정 시각은 기존 Spring Data JPA Auditing으로 관리한다.
- 고객이 확인하는 입금·출금·보상 기록은 Envers가 아니라 `account_transactions` 업무 테이블로 관리한다.

### 선택 이유

- 현재 프로젝트에는 Envers 의존성과 `@Audited` 엔티티가 없으므로 리비전 테이블을 생성해도 사용하는 코드가 없다.
- 금융 거래 기록은 엔티티 스냅샷이 아니라 명시적인 업무 의미와 멱등성 키를 가진 거래 내역이어야 한다.
- 사용하지 않는 감사 프레임워크와 테이블을 제거해 스키마와 운영 개념을 단순하게 유지한다.

### 감수한 한계

- 일반 엔티티 속성의 과거 스냅샷을 자동 조회하는 기능은 제공하지 않는다.
- 이후 규제·감사 요구로 일반 변경 이력이 필요해지면 별도의 감사 로그 설계를 다시 검토해야 한다.

## D-052 — 기능 우선·기능 내부 계층형 패키지 구조

> 현재 상태: 유지. 은행 애플리케이션은 기능 단위로 먼저 나누고 각 기능 내부를 계층으로 나눈다.

### 결정

- 최상위 기능 패키지는 `customer`, `account`, 이후 추가할 `transfer`로 구분한다.
- 각 기능 안에서 필요에 따라 `domain`, `application`, `infrastructure`, `presentation` 계층을 사용한다.
- 현재 존재하는 도메인 코드만 `customer.domain`과 `account.domain`으로 이동하고, 코드가 없는 빈 계층 패키지는 미리 만들지 않는다.
- `AccountTransaction`과 `AccountTransactionType`은 독립 송금이 아니라 계좌에 반영된 거래 기록이므로 `account.domain`에 둔다.
- JPA 설정은 `config`, JPA 공통 매핑 기반은 `support.persistence`에 둔다.
- 현재는 도메인 객체와 JPA 엔티티를 분리하지 않는다.

### 선택 이유

- 기능을 먼저 묶으면 하나의 업무 기능을 변경할 때 관련 코드를 가까운 위치에서 찾을 수 있다.
- 기능 내부 계층은 도메인 규칙, 유스케이스, 기술 구현, HTTP 경계를 구분할 수 있게 한다.
- 비어 있는 패키지를 미리 만들지 않으면 현재 규모보다 구조가 커지는 문제를 피할 수 있다.
- 도메인 객체와 JPA 엔티티를 별도로 만들지 않아 매핑 코드와 중복 모델의 비용을 줄인다.

### 의존 방향

- `presentation`은 `application`에 의존한다.
- `application`은 `domain`에 의존한다.
- `infrastructure`는 필요한 도메인 또는 애플리케이션 경계를 구현한다.
- `domain`은 `application`과 `presentation`에 의존하지 않는다.

### 감수한 한계

- JPA 어노테이션이 도메인 엔티티에 있으므로 프레임워크와 완전히 분리된 순수 도메인 계층은 아니다.
- 기능별 파일 수가 적은 초기에는 계층 디렉터리가 다소 세분화되어 보일 수 있다.

## D-053 — 은행 송금의 방향과 상태 속성 명칭

> 현재 상태: 유지. 은행 `Transfer`에서는 `source`와 `recipient`로 송금 방향을 표현하고 진행 상태 속성은 `state`로 표현한다.

### 결정

- 출금할 계좌는 `source_account_id`로 표현한다.
- 수취 은행과 수취 계좌는 `recipient_bank_code`, `recipient_account_number`로 표현한다.
- 은행 송금의 진행 상태 속성은 `status`가 아니라 `state`로 표현한다.
- 계좌 거래 기록의 상대 계좌 정보인 `other_bank_code`, `other_account_number`는 변경하지 않는다.
- 한국어 도메인 용어는 `송금 계좌`, `수취 은행`, `수취 계좌`를 사용한다.

### 선택 이유

- `recipient`는 단순한 전송 목적지보다 돈을 받는 역할을 표현하므로 금융 도메인의 `수취`라는 의미를 더 분명하게 전달한다.
- `sender_account`는 계좌가 송금 행위의 주체인 것처럼 읽힐 수 있으므로 돈이 출발하는 계좌에는 `source_account`를 사용한다.
- 은행 송금의 값은 단순 표시 정보가 아니라 허용되는 다음 전이를 결정하므로 `status`보다 `state`가 적합하다.
- `AccountTransaction`은 출금, 입금, 보상에 공통으로 사용되어 방향이 달라지므로 상대편을 중립적인 `other`로 유지한다.

### 감수한 한계

- `source`와 `recipient`는 문법적으로 완전히 대칭인 단어 조합은 아니다.
- 중앙 결제 모델의 명칭은 별도 설계 대상이므로 이번 결정만으로 `SettlementTransfer`의 필드명을 변경하지 않는다.

## D-054 — 결제 결과 전달 방식을 polling에서 동기 체인과 대사 조합으로 전환

> 현재 상태: 채택. 2026-09-18 결정. 현재 결정 문서의 §7, §9와 시나리오 사건 서술을 이 결정에 맞게 고친다. D-006의 일일 대사를 안전망으로 복원한다.

### 배경

- 1주차에 결제 결과 전달 방식으로 polling을 택했다. 통지 유실을 재조회로 복구할 수 있고, 수취 은행이 중단돼도 검증 대기 거래가 중앙에 남는다는 점을 근거로 삼았다.
- 2~3주차에 이 결정대로 구현했다. 수취 은행이 5초마다 중앙의 수취검증대기 목록을 조회해 승인·거절을 전달하고, 승인한 결제의 결과를 다시 조회해 입금하는 구조였다(이슈 #16, #17).
- 구현 도중 다음 문제가 드러났다.
  - 정상 경로가 대사처럼 보였다. 승인 응답에 최종 상태가 이미 들어 있는데도 그 응답을 버리고 5초 뒤 같은 결제를 다시 조회해 상태를 확인했다. 알고 있는 결과를 반복해서 물어보는 구조였다.
  - 처리량 상한이 통신 방식에 묶였다. 틱당 100건, 5초 주기로 약 20건/초가 상한이었고, 유입이 이를 넘으면 백로그가 무한히 늘었다. 처리 속도가 아니라 폴링 구조가 병목이었다.
  - 진행 중 기록마다 중앙에 HTTP를 한 번씩 보내는 네트워크 N+1이 생겼고, 결과 불명 건과 정상 건을 같은 주기로 같은 방식으로 다뤘다.
- 실제 은행 간 송금과 비교하면 차이가 분명했다. 실제 시스템은 정상 거래를 동기 체인로 끝내고, 응답을 받지 못한 거래만 확인 조회하며, 대사는 하루 한 번 안전망으로 수행한다. 우리는 셋 중 두 번째 방식만으로 전부를 처리하려 했다.
- 근본 원인은 "신뢰성이 중요하니 정상 상태에서도 오류가 잦을 것"이라는 전제였다. 이 전제 때문에 예외 경로에 맞는 방식을 정상 경로에 적용했다.

### 검토한 선택지

1. polling을 유지하고 커서, 배치 승인, 병렬 처리로 처리량만 올린다.
2. polling을 유지하되 승인 응답의 최종 상태로 즉시 입금하고, 결과 불명 건만 조회한다.
3. 중앙이 수취 은행을 동기 호출하는 체인로 정상 경로를 처리하고, 결과 불명 건만 확인 조회하며, 일일 대사를 안전망으로 둔다.

### 결정

- 선택지 3을 채택한다.
- 정상 경로는 동기 체인이다. 송금 은행이 중앙에 결제를 요청하면 중앙은 그 요청 안에서 수취 은행에 수취 검증을 요청하고, 응답에 따라 결제를 확정하고, 수취 은행에 입금을 통지한 뒤, 송금 은행의 요청에 최종 결과를 응답한다.
- 중앙이 수취 은행을 두 단계로 호출한다. 첫 호출은 수취 계좌 검증이며 고객 잔액을 변경하지 않는다. 둘째 호출은 결제완료 후 입금 통지다. 수취 가능 확인만으로 입금하지 않는다는 §7의 불변식과 결제잔액 부족 거절이라는 §8의 규칙을 그대로 유지하기 위한 분리다.
- 결과 불명 처리는 해당 건에 한정한 확인 조회로 한다. 송금 은행은 응답을 받지 못한 `송금중` 송금의 결과를 중앙에 조회한다. 수취 은행은 입금 통지를 받지 못한 미완료 수취 기록의 결과를 중앙에 조회한다. 중앙은 수취 검증 호출에 실패한 `수취검증대기` 결제를 재시도한다.
- 일일 대사를 안전망으로 채택한다. 은행은 하루 한 번 자기 기록과 중앙 결제 기록을 대조해 불일치를 탐지한다. 대사는 결과 전달 수단이 아니다.
- 로컬 반영 규칙은 결과가 동기 응답, 확인 조회, 대사 중 어느 경로로 도착했는지에 의존하지 않는다. 이 원칙은 1주차 결정에서 그대로 가져온다.

### 선택 이유

- 정상 경로의 지연이 폴링 주기가 아니라 요청 처리 시간으로 내려간다. 고객은 송금 요청 한 번으로 결과를 받는다.
- 처리량 상한이 폴링 틱이 아니라 요청 처리 능력이 된다.
- 결과 불명 건만 조회하므로 조회 대상이 작고, 정상 건과 예외 건이 다른 경로를 탄다. 실제 은행의 미확인 거래 조회와 같은 성격이다.
- 실제 금융 시스템의 구조와 같아 이후 장애 복구와 부하 실험의 결과를 실제 사례와 비교할 수 있다.
- 기존 불변식 17개가 모두 유지된다. 바뀌는 것은 통신 방향과 트리거이며 잔액, 거래 기록, 멱등 규칙, 상태 전이는 그대로다.

### 선택지 1, 2를 택하지 않은 이유

- 선택지 1은 병목을 넓히지만 정상 경로가 대사라는 구조 자체는 남는다. 처리량은 늘어도 지연은 폴링 주기 아래로 내려가지 않는다.
- 선택지 2는 수취 은행 쪽 어색함은 줄이지만 송금 은행은 여전히 정상 경로에서 조회에 의존한다. 반쪽 전환이라 두 방식이 공존하는 복잡성이 남는다.

### 감수한 한계

- 중앙이 은행의 주소를 알아야 하고, 수취 은행이 중앙의 호출을 받는 API를 열어야 한다. 기관 인증은 여전히 범위 밖이므로 현재는 은행이 중앙을 호출하는 것과 같은 신뢰 수준이다.
- 중앙에 수취 검증 호출 실패 시 재시도 책임이 생긴다. 폴링에서는 수취 은행이 복구 후 스스로 가져갔지만 이제 중앙이 자기 미완료 작업을 다시 밀어야 한다.
- 송금 은행의 요청이 수취 은행 응답까지 기다리므로 체인 전체의 시간 상한과 타임아웃 시 "처리 중" 응답 정책이 필요하다.
- 이슈 #17, #18의 골격이 바뀌고 이미 머지된 #16의 대기 목록 조회와 승인·거절 전달은 결과 불명 복구 경로로 역할이 축소된다.

### 재사용하는 것

- 중앙의 결제 접수 멱등 처리, 승인·거절의 잔액 이동 트랜잭션.
- 은행의 `Receipt` 모델과 입금 트랜잭션. 검증 시점에 기록을 만들고 입금 통지에서 완료하는 멱등 입금 기록으로 쓴다.
- 은행의 `RestClient` 예외 변환 방식. 중앙이 은행을 호출하는 클라이언트에 그대로 적용한다.

### 보류 사항

- 체인 전체의 시간 상한과 수취 은행 응답 지연 시 송금 은행에 돌려줄 응답의 형태.
- 중앙의 수취 검증 재시도 주기와 한도.
- 일일 대사의 실행 시각, 마감 기준, 지연 거래 처리, 불일치 발견 시 자동 복구와 운영 확인의 경계(D-006 보류 사항과 동일).
