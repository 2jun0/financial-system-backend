# 도메인 결정

## 문서 목적

현재 합의된 도메인 경계, 데이터 소유권, 거래 규칙과 불변식을 한 문서에서 확인할 수 있도록 정리한다.

이 문서에는 현재 확정된 설계만 기록한다. 설계 과정, 폐기된 대안과 아직 결정하지 않은 내용은 포함하지 않는다.

## 1. 프로젝트 범위

### 결정

- 시스템은 고객, 계좌, 잔액과 거래 기록을 관리한다.
- 고객은 자신이 소유한 계좌에서 다른 은행 계좌로 보내는 송금을 독립적으로 요청할 수 있다.
- 고객이 별도로 실행하는 입금·출금 기능은 구현하지 않는다. 출금과 입금은 계좌 생성 시 은행 내부 이체 또는 은행 간 송금을 반영한 계좌 금액 변동이다.
- 실제 금융기관이나 실제 금융망과 연동하지 않는다.
- 실제 자금 이동 대신 은행 간 결제 거래를 기록하는 모의 중앙 결제 시스템을 구현한다.
- 외부 자금 이동과 로컬 계좌 반영 사이에서 발생하는 부분 실패, 중복 처리, 동시성, 결과 불명과 복구 문제를 시스템의 책임 범위에 포함한다.

### 선택 이유

- 실제 금융망의 규제와 연동 구현을 제외하면서도 금융 거래 백엔드의 핵심 신뢰성 문제를 재현할 수 있다.
- 결제망 자체보다 외부 결제망에 참가하는 은행 백엔드가 로컬 계좌와 중앙 결제 기록 사이의 정합성을 유지하는 문제에 집중할 수 있다.
- 정합성, 트랜잭션, 멱등성, 동시성과 장애 복구라는 8주 프로젝트의 목적을 유지할 수 있다.

### 제외 범위

- 실제 금융기관 및 금융망 연동
- 실제 중앙은행 계좌와 자금 이동
- 은행 간 유동성 관리, 담보와 차액결제
- 법적 결제완결성 구현
- ISO 20022 전체 규격 구현
- 블록체인 합의와 분산 원장 운영
- ATM 및 창구 현금 입금
- 같은 은행 계좌 사이의 송금(MVP 이후 선택 기능)
- 고객이 송금 은행에 보내는 요청의 멱등 키. 같은 고객 요청이 다시 들어오면 새 송금으로 처리한다

## 2. 시스템 구성과 데이터 소유권

### 은행 시스템

- 동일한 은행 애플리케이션을 서로 다른 은행을 나타내는 두 인스턴스로 실행한다.
- 두 은행 인스턴스는 각각 은행 식별자와 독립된 DB를 가진다.
- 고객, 계좌, 잔액과 고객 계좌의 거래 기록은 각 은행이 소유한다.
- 한 은행은 다른 은행의 DB를 직접 읽거나 수정하지 않는다.
- 각 은행의 로컬 거래는 해당 은행의 DB 트랜잭션 경계 안에서만 처리한다.

### 모의 중앙 결제 시스템

- 두 은행 사이에 은행 시스템과 분리된 모의 중앙 결제 시스템을 둔다.
- 은행 간 송금은 송금 은행이 수취 은행을 직접 호출하는 방식으로 처리하지 않는다.
- 중앙 결제 시스템은 고객 계좌가 아니라 은행 간 결제 거래와 그 최종 결과를 관리한다.
- 중앙 결제 시스템은 은행 간 결제가 완료됐는지 또는 거절됐는지를 확정하는 권위 있는 시스템이다.
- 중앙 시스템에서 완료된 결제는 최종적인 결과이며, 개별 은행의 로컬 처리 지연이나 실패로 되돌리지 않는다.
- 중앙 결제 시스템은 참가 은행마다 하나의 결제계좌와 현재 결제잔액을 관리한다.
- 데이터 모델에서는 참가 은행마다 원화 결제잔액이 하나뿐이므로 별도 결제계좌 모델을 만들지 않고 `Bank.balance`로 저장한다.
- 고객 계좌와 은행 결제계좌는 서로 다른 계좌이며, 중앙 결제 시스템은 고객 계좌의 잔액을 소유하거나 변경하지 않는다.
- 결제 완료 시 송금 은행 결제계좌 차감, 수취 은행 결제계좌 증가와 거래의 완료 기록을 하나의 중앙 DB 트랜잭션으로 처리한다.
- 송금 은행의 결제잔액이 부족하면 결제를 완료하지 않고 거절한다.
- 은행별 고객 계좌와 잔액은 계속 각 은행이 소유한다.
- 은행과 중앙 결제 시스템은 정의된 외부 인터페이스로만 통신하며 DB를 공유하지 않는다.

### 선택 이유

- 실제 은행 간 송금이 공동망이나 중앙 결제 인프라를 거치는 구조를 축소해 표현할 수 있다.
- 중앙 시스템의 거래 기록과 각 은행의 로컬 계좌 반영은 하나의 DB 트랜잭션으로 묶이지 않으므로 프로젝트가 다루려는 부분 실패 문제가 남는다.
- 중앙 시스템이 고객 계좌까지 소유하지 않아 은행의 독립적인 데이터 경계를 유지한다.
- 은행의 로컬 상태가 아니라 중앙 결제 결과를 은행 간 자금 이동의 기준으로 삼아 개별 은행 장애가 전역 결과를 임의로 바꾸지 못하게 한다.
- 은행별 결제잔액의 차감과 증가를 원자적으로 처리하여 중앙 결제의 완료가 실제 은행 간 원장 변동을 뜻하게 한다.
- 복잡한 유동성 관리 없이도 결제잔액 부족, 중복 결제와 동시 결제 상황의 정합성을 검증할 수 있다.

### 은행 결제계좌 제외 범위

- 담보와 일중대출
- 당좌대월
- 차액결제
- 결제 우선순위와 유동성 대기열

### 용어 구분

- `송금`은 고객이 자신의 계좌에서 다른 은행 계좌로 돈을 보내는 전체 업무를 뜻한다.
- `결제`는 중앙 결제 시스템이 두 은행의 결제잔액을 이동하고 은행 간 자금 이동의 결과를 확정하는 처리를 뜻한다.
- 송금 은행이 중앙 결제 시스템에 은행 간 결제를 요청하는 행위는 `결제를 요청한다(request settlement)`라고 표현한다. 현재 모델은 별도의 지급지시를 두지 않고 `Settlement`가 결제 요청과 상태를 함께 관리한다.
- `출금`과 `입금`은 각 은행이 고객 계좌에 반영하는 로컬 잔액 변동과 그 기록을 뜻한다.
- 중앙 결제 거래의 최종 상태는 `결제완료`와 `결제거절`로 표현한다. `거래완료`는 송금 은행과 수취 은행의 로컬 반영까지 모두 끝난 것으로 오해할 수 있어 상태명으로 사용하지 않는다.

### 참가 은행에 대한 신뢰 가정

- 참가 은행은 사전에 식별되고 허용된 정상 주체이며, 의도적으로 허위 거래를 만들거나 처리 결과를 조작하지 않는다고 가정한다.
- 참가 은행의 애플리케이션, 프로세스와 네트워크는 신뢰하지 않는다.
- 서버 중단, 응답 유실, 메시지 중복, 처리 지연, 순서 변경과 동시 처리는 언제든 발생할 수 있다고 가정한다.
- 중앙 결제 시스템은 이러한 운영 장애에도 하나의 거래가 중복 결제되거나 서로 다른 최종 결과를 갖지 않도록 해야 한다.

### 신뢰 가정 선택 이유

- 이 프로젝트의 목적은 악의적인 금융기관과 사기 거래를 방어하는 것이 아니라 정상 참가자의 시스템 장애에서 정합성을 유지하는 방법을 실험하는 것이다.
- 악의적인 참가자까지 가정하면 은행별 결제 잔액, 메시지 서명, 부인 방지, 규제와 감사 절차까지 범위가 확대된다.
- 운영 장애를 신뢰하지 않는 가정만으로도 부분 실패, 멱등성, 동시성, 재시도와 복구 문제를 충분히 검증할 수 있다.

## 3. 고객과 계좌

### 결정

- 고객은 회원가입하고 로그인할 수 있다.
- 고객마다 시스템 내부의 고유 식별자가 존재한다.
- 한 고객은 여러 계좌를 소유할 수 있다.
- 로그인한 고객은 자신이 소유한 계좌만 조회하고 거래할 수 있다.
- 회원가입 시 계좌를 자동으로 개설하지 않는다.
- 계좌를 개설하면 같은 은행에 미리 준비한 시연용 고객의 계좌에서 새 고객 계좌로 100,000원을 이체한다.
- 이 은행 내부 이체는 계좌 생성 시에만 사용하며, 일반 고객이 요청하는 동일 은행 송금은 MVP에서 계속 제외한다.
- 시연용 계좌도 별도 계좌 유형이 아닌 고객 소유 계좌이며, 모든 계좌의 고객 식별자는 필수다.
- 시연용 고객과 계좌는 개발·시연 환경의 초기 데이터로만 준비한다.

### 선택 이유

- 고객과 계좌 소유 관계를 명시하여 거래 권한을 검증할 수 있다.
- 한 고객이 여러 계좌를 관리하는 소유 관계를 표현할 수 있다. 같은 은행 계좌 사이의 송금은 이 관계와 별개로 MVP에서 제외한다.
- 고객 가입과 금융 계좌 개설을 서로 다른 생명주기로 다룬다.
- 실제 외부 입금 기능 없이도 송금 흐름을 시작할 수 있고, 새 고객 계좌의 100,000원이 어느 계좌에서 이체됐는지 기록으로 설명할 수 있다.
- 시연 편의를 위한 자금 출처 때문에 운영 도메인에 `은행 자금 계좌` 유형을 추가하지 않는다.
- 인증 범위를 최소화하여 거래 신뢰성 실험이 인증 기능 구현에 가려지는 것을 방지한다.

### 파생 불변식

- 모든 계좌는 정확히 한 명의 고객에게 소유되어야 하며 고객 식별자가 반드시 존재해야 한다.
- 인증된 고객은 자신이 소유하지 않은 계좌를 조회하거나 해당 계좌에서 자금을 이동시킬 수 없다.

### 제외 범위

- 회원 탈퇴와 계정 복구
- 비밀번호 재설정과 이메일 인증
- 소셜 로그인
- KYC
- 계좌 정지, 삭제와 해지 생명주기

## 4. 계좌 잔액과 거래 기록

### 결정

- 계좌에 현재 잔액을 저장한다.
- 계좌의 금액 변동을 설명할 수 있는 거래 기록을 함께 저장한다.
- 송금의 진행 상태를 관리하는 송금 기록과 계좌 잔액 변동의 근거인 계좌 거래 기록을 분리한다.
- 하나의 송금은 출금과 거절에 따른 보상 등 여러 계좌 거래 기록과 연결될 수 있다.
- 계좌 거래 기록의 반영 종류는 출금을 뜻하는 `DEBIT`, 입금을 뜻하는 `CREDIT`, 결제거절에 따른 출금 반환을 뜻하는 `COMPENSATION`으로 구분한다.
- 계좌 거래 기록의 금액은 잔액 변동량으로 저장하여 출금은 음수, 입금과 보상은 양수로 표현한다.
- 계좌 거래 기록의 금액에 0은 허용하지 않는다.
- 거래 기록은 잔액의 근거이고, 현재 잔액은 빠른 조회와 거래 처리를 위한 값이다.
- 잔액 검증과 잔액 변경은 같은 로컬 DB 트랜잭션에서 수행한다. 같은 계좌에 대한 요청이 동시에 처리되어도 잔액이 0보다 작아지거나 거래 기록과 어긋나지 않아야 한다. 잠금 또는 조건부 갱신 방식은 동시성 실험에서 결정한다.
- 중앙 결제의 송금 은행 잔액은 잔액 조건을 포함한 UPDATE로 차감하고, 수취 은행 잔액은 DB에서 직접 더한다. 두 잔액 변경과 결제 상태 변경은 같은 트랜잭션에서 처리한다. 결제 기록을 생성하는 트랜잭션과 잔액을 반영하는 트랜잭션은 모두 은행 ID 오름차순으로 두 은행 행을 SELECT FOR UPDATE한 뒤 처리한다. 외부 은행 HTTP 호출 중에는 잠금을 유지하지 않으며, 잔액 반영 트랜잭션은 잠금을 획득한 뒤 만료 여부를 다시 확인한다. 데드락 재시도는 적용하지 않는다.
- 새 고객 계좌에 100,000원을 직접 설정하거나 `초기 자금`이라는 계좌 거래 기록을 생성하지 않는다.
- 새 고객 계좌에 반영된 100,000원은 시연용 고객 계좌에서 들어온 내부 이체 입금 기록으로 남긴다.
- 송금 은행에서 송금액을 차감하면 출금 기록을 남긴다.
- 중앙 결제가 완료된 거래를 수취 은행이 고객 계좌에 반영하면 입금 기록을 남긴다.
- 고객은 자신이 소유한 계좌에서 위 출금·입금 기록을 조회할 수 있다.
- 모든 금액은 원화로 가정하고 통화 자체를 모델링하지 않는다.
- 고객 계좌의 입금 기록은 계좌 생성 시 시연용 고객 계좌에서 들어온 내부 이체와, 다른 은행에서 중앙 결제 시스템을 거쳐 들어온 은행 간 송금을 반영한다.
- 고객이 외부 거래 정보를 직접 입력하여 입금을 발생시키는 기능은 허용하지 않는다.
- 외부 거래 정보를 입력하는 도구를 만들더라도 시연과 테스트를 위한 편의 기능으로만 취급한다.

### 선택 이유

- 거래 기록으로 자금 이동을 추적하고 현재 잔액의 변동 근거를 검증할 수 있다.
- 송금 하나에서 출금과 보상처럼 서로 다른 잔액 변동이 발생할 수 있으므로, 송금 상태와 각 잔액 변동을 독립적으로 추적해야 한다.
- 반영 종류를 구분하면 같은 외부 거래 ID에서 정당한 출금과 보상을 각각 한 번씩 허용하면서 같은 반영의 중복은 막을 수 있다.
- 거래마다 전체 기록을 합산하지 않고 현재 잔액을 저장하여 조회와 거래 처리 성능을 확보한다.
- 현금 입금과 외화 문제를 제외하여 거래 정합성이라는 핵심 범위에 집중한다.

### 파생 불변식

- 계좌의 현재 잔액은 해당 계좌에 반영된 거래 기록으로 설명할 수 있어야 한다.
- 거래 기록을 삭제하거나 덮어써서 잔액의 변동 근거를 없애서는 안 된다.
- 현재 잔액과 거래 기록의 갱신은 하나의 로컬 DB 트랜잭션으로 처리해야 한다.
- 은행 내부 이체, 송금 출금과 수취 입금은 각각 대응하는 거래 기록 없이 잔액만 변경해서는 안 된다.

## 5. 은행 간 결제 거래의 식별과 멱등성

### 결정

- 하나의 은행 간 결제 거래에는 해당 거래를 안정적으로 식별하는 외부 거래 ID가 존재한다.
- 데이터 모델에서는 이 자금 이동 식별자의 속성명을 `transfer_key`로 사용하며, DB 트랜잭션 식별자를 의미하지 않는다.
- 동일한 결제 거래를 재전송하거나 다시 조회하더라도 외부 거래 ID는 유지한다.
- 동일한 외부 거래 ID의 같은 반영 종류는 고객 계좌와 로컬 거래 기록에 한 번만 반영해야 한다. 반영 종류는 송금 출금, 수취 입금과 거절에 따른 보상을 구분한다.
- 동일한 외부 거래 ID가 금액이나 계좌 등 다른 거래 내용과 함께 사용되면 정상 재시도가 아니라 충돌로 취급한다.
- 송금 은행은 송금 생성 시각을 `transferCreatedAt`으로 전달하고, 같은 결제를 재전송할 때 외부 거래 ID와 송금 생성 시각을 함께 유지한다.
- 개별 전송 시도를 추적할 ID가 필요하면 외부 거래 ID와 별도로 관리한다.
- 은행의 로컬 거래 기록은 어떤 중앙 결제 거래를 근거로 반영했는지 추적할 수 있어야 한다.
- 같은 외부 거래 ID와 같은 반영 종류의 계좌 거래 기록은 저장소의 고유 제약으로 중복을 막는다. 고유 제약 위반은 이미 반영된 것으로 처리하고 오류로 응답하지 않는다.
- 같은 외부 거래 ID로 같은 내용의 결제 요청이 다시 오면 중앙 결제 시스템은 새 검증을 시작하지 않고 현재 상태를 응답한다.

### 선택 이유

- 응답 유실, 재전송, 확인 조회와 장애 후 재처리가 발생해도 중복 입금과 중복 출금을 막을 수 있다.
- 하나의 자금 이동과 여러 번의 통신 시도를 구분할 수 있다.
- 중앙 결제 기록과 은행의 로컬 반영을 연결해 문제 거래를 추적할 수 있다.

### 파생 불변식

- 동일한 외부 거래 ID와 같은 반영 종류로 계좌 잔액을 두 번 변경해서는 안 된다.
- 하나의 송금은 여러 계좌 거래 기록을 가질 수 있지만, 같은 외부 거래 ID와 같은 반영 종류의 기록은 중복되어서는 안 된다.
- 동일한 외부 거래 ID의 내용 충돌을 정상 거래로 반영해서는 안 된다.

## 6. 은행 간 송금의 금액 처리와 결과 불명

### 결정

- 송금액은 0보다 큰 양의 정수만 허용한다.
- 송금 계좌의 잔액이 송금액보다 부족하면 송금 요청을 거절한다.
- 금액 형식과 고객 잔액은 송금 거래 생성과 출금 전에 검증한다.
- 이 사전 검증에서 거절된 요청은 송금 거래나 계좌 거래 기록으로 생성하지 않는다.
- 송금 시작 시 송금 계좌에서 금액을 한 번 출금한다.
- 출금 후 거래 결과가 아직 확정되지 않은 거래는 `송금중`으로 추적한다.
- 송금 은행의 최소 거래 상태는 `송금중`, `성공`, `실패`이다.
- 중앙 결제 시스템이 은행 간 결제를 완료로 확정하면 송금 은행은 해당 송금을 성공으로 확정한다.
- 중앙 결제 시스템이 결제를 거절로 확정했거나, 결제 만료 후 권위 있는 확인 조회에서 기록이 없음을 응답한 경우에만 송금 은행은 별도의 보상 거래로 출금액을 반환하고 송금을 `실패`로 확정한다.
- `실패`는 `송금중`에 진입한 뒤 중앙의 결제거절 또는 만료 후의 권위 있는 `기록 없음`을 확인하고 출금 보상까지 완료한 송금에만 사용한다.
- 완료로 확정된 중앙 결제는 수취 은행의 고객 계좌 반영이 지연되거나 실패해도 거절이나 실패로 되돌리지 않는다.
- 송금 은행이 중앙 결제 요청의 응답을 받지 못했거나 확인 조회에 실패했다는 이유만으로 실패 처리하거나 보상하지 않는다.
- 중앙 결제 시스템이 수취 가능 여부를 제한 시간 안에 확인하지 못해 결제를 `결제거절`로 확정한 경우에는 그 최종 결과를 근거로 송금 은행이 보상할 수 있다. 이는 송금 은행의 추측이 아니라 중앙 결제 시스템의 정책적 결정이다.
- 중앙 결제 시스템이 결제 만료 시간을 넘긴 요청이나 `수취검증대기` 결제를 `결제거절`로 확정하면 이는 추측이 아니라 규칙에 따른 확정이며, 송금 은행은 이 거절을 근거로 보상하고 송금을 `실패`로 확정한다.
- 결제 만료 후 중앙 결제 시스템의 권위 있는 확인 조회가 기록이 없음을 응답하면, 만료된 요청은 이후 도착해도 결제될 수 없으므로 송금 은행은 이를 근거로 보상하고 송금을 `실패`로 확정한다.
- 송금 결과를 확정할 근거를 확인할 수 없는 거래는 `송금중`을 유지한다.

### 최소 상태 전이

```text
송금중 -- 중앙 결제완료 확인 --> 성공
송금중 -- 중앙 결제거절 확인 + 출금 보상 --> 실패
송금중 -- 만료 후 중앙 기록 없음 확인 + 출금 보상 --> 실패
```

`성공`과 `실패`는 최종 상태다. 송금 은행이 겪은 요청 timeout이나 조회 실패만으로 `송금중`에서 `실패`로 전이하지 않는다.

### 선택 이유

- 결과 불명 상태에서 출금을 보상하면 지연된 거래가 이후 수취 은행에 반영되어 중복 지급이 발생할 수 있다.
- 거래를 억지로 끝내는 것보다 근거 없는 금액 이동을 막는 안전성을 우선한다.
- 선출금 방식은 부분 실패, 결과 불명, 멱등 처리와 보상 거래를 명시적으로 실험할 수 있다.
- 돈이 움직이기 전의 요청 거절과 이미 시작된 송금의 실패를 분리하면 계좌 거래 기록은 실제 잔액 변동만 설명하고 `실패`의 의미도 한 가지로 유지된다.
- 보류 금액 모델은 장부 잔액과 사용 가능 잔액, 보류·확정·해제의 추가 생명주기를 요구하므로 현재 범위에서 제외한다.
- 중앙 결제 결과가 은행 간 자금 이동의 권위 있는 기준이어야 송금 은행이 수취 은행의 로컬 상태를 추측하여 보상하는 위험을 피할 수 있다.
- 결제 완료 후 수취 계좌 반영 실패는 결제 자체의 실패가 아니라 수취 은행이 반드시 재처리해야 할 로컬 미반영 문제로 분리한다.

### 파생 불변식

- 하나의 송금에 대한 출금은 한 번만 실행되어야 한다.
- 송금으로 인해 고객 계좌 잔액이 0보다 작아져서는 안 된다.
- 결과를 확인할 수 없다는 이유만으로 `송금중` 거래를 실패로 변경해서는 안 된다.
- 실패가 확정되지 않은 송금에는 보상 거래를 실행해서는 안 된다.
- 보상 거래는 하나의 송금에 한 번만 실행되어야 한다.
- 성공한 송금에는 보상 거래가 존재해서는 안 된다.
- 중앙 결제 시스템이 완료로 확정한 송금에는 보상 거래를 실행해서는 안 된다.
- `송금중`인 금액을 포함하여 자금의 위치를 추적할 수 있어야 한다.
- 중앙 결제 전후 모든 은행 결제계좌 잔액의 합계는 보존되어야 한다.

## 7. 수취 계좌 사전 검증

### 결정

- 중앙 결제 시스템은 수취 은행의 확인 없이 은행 간 결제를 완료해서는 안 된다.
- 수취 은행은 중앙 결제 전에 수취 고객 계좌가 존재하여 입금 대상이 될 수 있는지 검증한다.
- 중앙 결제 시스템은 결제를 `수취검증대기`로 저장한 뒤 로컬 DB 트랜잭션 밖에서 수취 은행에 수취 계좌 검증을 한 번 요청한다.
- 수취 은행이 수취 가능을 응답하면 중앙 결제 시스템은 결제잔액을 확인한 뒤 결제를 완료한다.
- 수취 은행이 수취 불가를 응답하면 중앙 결제 시스템은 결제를 거절한다.
- 수취 은행이 명시적으로 응답한 `수취 가능`과 `수취 불가`만 업무 결과로 해석한다. timeout, 연결 실패, HTTP 오류, 해석할 수 없는 응답 또는 제한 시간 안에 응답을 확인하지 못한 경우에는 중앙 결제 시스템이 결제를 거절한다. 이 거절은 수취 은행의 명시적 거절이 아니라, 제한 시간 안에 수취 가능을 확인하지 못했을 때 적용하는 중앙 결제 시스템의 정책적 거절이다.
- 중앙 결제 시스템은 실패한 수취 검증 요청을 재시도하지 않는다. 수취 검증 호출에 사용하는 HTTP 읽기 타임아웃은 10초이며, 중앙 결제 기록의 생성 시각부터 계산하는 별도의 수취 검증 기한은 두지 않는다.
- 수취 은행의 수취 가능 확인은 고객 계좌 입금이 아니며 고객 잔액을 변경하지 않는다.
- 수취 가능 응답은 현재 상태가 `수취검증대기`이고 전체 결제 만료 시간이 지나지 않은 경우에만 반영할 수 있다. timeout으로 HTTP 호출이 종료된 뒤의 응답은 별도의 검증 결과로 처리하지 않는다.

### 선택 이유

- 수취 계좌가 존재하는지 확인하지 않고 결제를 완료하면 수취 은행이 고객에게 귀속시킬 수 없는 자금을 받게 된다.
- 수취 가능 여부를 결제 전에 확인하면 중앙 결제 완료 후 수취 은행이 계좌 부재를 이유로 결제를 되돌리는 상황을 방지할 수 있다.
- 사전 검증과 실제 입금을 분리하여 중앙 결제의 최종성을 유지하면서 수취 은행의 로컬 장애는 재처리 가능한 문제로 남긴다.
- 검증을 중앙이 한 번만 요청하고 제한 시간 안에 확정하면 수취 은행의 지연이 중앙 결제 시스템의 작업 적체와 반복 호출로 확대되는 것을 막을 수 있다.
- 통신 장애를 거절로 확정하면 일시적 장애에도 정상 거래가 거절될 수 있다. 현재 프로젝트는 가용성보다 결제 처리 시간의 상한과 중앙 시스템의 부하 통제를 우선하여 이 trade-off를 수용한다.
- 결제 결과 통지도 중앙 결제 시스템이 수취 은행에 보내므로 검증과 결과 반영이 같은 통신 방향과 복구 원칙을 공유한다.

### 파생 불변식

- 수취 은행의 수취 가능 확인이 없는 거래를 중앙 결제 완료로 변경해서는 안 된다.
- 수취 불가로 확정된 거래에서는 은행별 결제잔액과 수취 고객 잔액을 변경해서는 안 된다.
- 제한 시간 안에 수취 가능을 확인하지 못해 거절된 거래에서도 은행별 결제잔액과 수취 고객 잔액을 변경해서는 안 된다.
- 수취 가능 확인만으로 수취 고객 계좌 잔액을 증가시켜서는 안 된다.
- `수취검증대기`에서 최종 상태로의 변경은 조건부로 한 번만 성공해야 하며, 중복된 처리로 이미 확정된 상태를 변경해서는 안 된다.

## 8. 중앙 결제 상태와 전이

### 결정

- 중앙 결제 거래의 최소 상태는 `수취검증대기`, `결제완료`, `결제거절`이다.
- 결제 요청은 외부 거래 ID와 거래 내용 외에 송금 은행의 송금 생성 시각인 `transferCreatedAt`을 포함한다. 중앙 결제와 수취 기록은 이 값을 `transfer_created_at`으로 저장한다.
- 결제 만료 시각은 송금 생성 시각에서 300초가 지난 시각이다. 현재 시각이 만료 시각과 같거나 이후이면 만료로 판단한다. 중앙 결제 기록이 생성된 시각으로 기한을 연장하지 않는다.
- 중앙 결제 시스템은 처음 결제 기록을 만들 때와 수취 검증 호출이 끝난 뒤에 만료 여부를 확인한다. 두 검사 사이의 네트워크 지연으로 기한을 넘긴 요청도 거절한다.
- 시각은 `java.time.Instant`로 표현하고 현재 시각은 UTC `Clock`으로 구한다. 현재 만료 검증에는 시계 오차에 대한 유예 시간을 두지 않는다.
- 중앙의 HTTP 읽기 타임아웃 10초는 수취 검증 호출의 응답 대기를 제한하며, 송금 생성 시각을 기준으로 한 전체 결제 만료 시간 300초와는 구분한다.
- 만료 전에 처음 접수한 결제 요청은 `수취검증대기`로 생성한다.
- 처음 접수했을 때 이미 만료된 결제 요청은 수취 검증과 결제잔액 이동을 시작하지 않고 `결제거절`로 생성한다.
- 수취 은행이 수취 가능을 확인하고 송금 은행의 결제잔액이 충분하면, 두 은행 결제잔액 이동과 함께 `결제완료`가 된다.
- 수취 은행이 수취 계좌가 없다고 확정하거나 송금 은행의 결제잔액이 부족하면 `결제거절`이 된다.
- 수취 검증 요청이 실패하거나 수취 가능 응답을 제한 시간 안에 확인하지 못하면 `결제거절`이 된다.
- `수취검증대기`가 결제 만료 시간을 넘기면 중앙 결제 시스템이 `결제거절`로 변경한다.
- 수취 불가 응답을 받으면 송금 은행의 결제잔액을 확인하지 않고 `결제거절`로 변경한다.
- `수취검증대기`에서 최종 상태로의 변경은 현재 상태가 `수취검증대기`인 경우에만 수행한다. 이미 최종 상태이면 변경하지 않는다. 결제완료로 변경할 때는 결제 만료 여부도 확인한다. 만료 처리가 지연되어 상태가 아직 대기여도 만료된 결제를 완료해서는 안 된다.
- 결제잔액 이동은 `결제완료`로의 변경이 실제로 이루어진 같은 중앙 DB 트랜잭션에서만 수행한다.
- 정상 처리에서는 한 번의 수취 검증 요청이 끝나면 `결제완료` 또는 `결제거절`을 응답한다. 송금 은행이 응답을 받지 못한 경우에는 중앙 결제 결과를 추측하지 않고 `송금중`을 유지한다.
- `결제완료`와 `결제거절`은 최종 상태다.
- 은행 결제잔액 부족은 도메인 거절 조건으로 유지하되, MVP 정상 흐름에서는 결제잔액이 충분하다고 가정하고 유동성 회복 절차는 구현하지 않는다.

### 최소 상태 전이

```text
신규 결제 요청 -- 접수 시 이미 만료 ----------> 결제거절
수취검증대기 -- 수취 가능 + 결제잔액 충분 --> 결제완료
수취검증대기 -- 수취 불가 확정 ----------> 결제거절
수취검증대기 -- 검증 요청 실패/제한 시간 초과 --> 결제거절
수취검증대기 -- 결제잔액 부족 ----------> 결제거절
수취검증대기 -- 결제 만료 시간 초과 ----> 결제거절
```

### 선택 이유

- 수취 계좌 검증과 중앙 결제 결과를 구분하면서도 MVP에 필요하지 않은 중간 상태를 늘리지 않는다.
- 수취 검증의 실패를 같은 요청 안에서 최종 거절로 끝내 중앙 결제 시스템에 장기간 남는 검증 대기 작업과 검증 재시도 부하를 만들지 않는다.
- 중앙 결제 시스템이 하나의 만료 기준을 집행하면 송금 은행이 통신 실패만으로 결과를 추측하지 않아도 되고, 지연된 요청이 만료 후 새 결제를 시작하는 것도 막을 수 있다.
- 중앙 결제 시스템이 만료된 요청을 완료하지 않는다는 규칙을 집행하므로, 송금 은행은 만료 후의 권위 있는 `기록 없음`을 최종 근거로 사용할 수 있다.
- 중앙 결제의 최종 결과를 송금 은행은 결제 요청의 응답으로, 수취 은행은 결제 결과 통지로 받고, 받지 못한 경우 확인 조회로 각자의 로컬 상태를 수렴시킬 수 있다.
- 결제잔액 부족 규칙은 중앙 원장의 정합성을 위해 필요하지만, 유동성 관리까지 구현하면 8주 프로젝트의 범위를 벗어난다.

## 9. 결제 결과 전달과 로컬 반영

### 결정

- 결제 결과는 세 경로로 전달한다. 정상 경로에서는 송금 은행에 결제 요청의 응답으로, 수취 은행에 결제 결과 통지로 전달한다. 정상 경로로 결과를 받지 못한 시스템은 그 건에 한정한 확인 조회로 결과를 확인한다. 두 경로가 놓친 불일치는 대사로 탐지한다.
- 정상 경로를 동기 체인이라 부른다. 송금 은행의 결제 요청 하나를 처리하는 동안 중앙 결제 시스템이 수취 은행에 수취 계좌 검증을 요청하고, 검증 결과에 따라 결제를 확정하고, 수취 은행에 `결제완료` 또는 `결제거절` 결과를 통지한 뒤, 송금 은행의 요청에 최종 결과를 응답하는 흐름이다. 중앙은 명시적 수취 불가를 포함해 수취 검증을 시도한 결제의 확정 결과를 한 번 통지한다. 처음 접수할 때 이미 만료되어 수취 검증을 시작하지 않은 요청에는 결과를 통지하지 않는다. 수취 은행은 거절 결과에 대응하는 수취 기록이 있을 때만 입금 없이 `실패`로 변경하고, 기록이 없으면 새로 생성하지 않고 처리를 종료한다.
- 각 시스템은 다른 시스템을 호출하거나 응답하기 전에 자기 상태를 먼저 저장한다.
- 외부 시스템에 대한 네트워크 요청은 로컬 DB 트랜잭션에 포함하지 않는다.
- 로컬 DB 트랜잭션 커밋 전에 프로세스가 중단되면 해당 변경은 모두 롤백하고, 복구 작업이 기존 미확정 기록을 다시 처리한다.
- 로컬 DB 트랜잭션 커밋 후 외부 요청 전에 프로세스가 중단되면 이미 저장된 미확정 기록을 복구 작업이 찾아 해당 흐름의 복구 규칙에 따라 종결한다. 외부 요청을 수행할 수도 있고, 제한 시간을 넘겼다면 거절할 수도 있다. 다만 이미 최종 상태인 중앙 결제의 결과 통지는 복구 작업이 다시 보내지 않고 수취 은행의 확인 조회로 복구한다. 커밋된 변경을 롤백된 것으로 간주하지 않는다.
- 복구 처리 중 같은 장애가 반복되어도 로컬 트랜잭션은 부분 변경을 남기지 않으며, 미확정 기록은 다음 복구 대상에 남는다. 이 공통 동작은 처리 지점별 시나리오로 반복하지 않는다.
- 송금 은행은 결제 요청의 응답으로 받은 최종 결과를 근거로 송금을 `성공` 또는 `실패`로 변경한다. 응답을 받지 못하면 `송금중`을 유지한다.
- 수취 은행은 검증 요청을 받을 때 수취 기록을 `수취중`으로 기록하고 송금 생성 시각도 함께 저장한다. 결제 결과 통지로 `결제완료`를 받으면 그 기록을 근거로 고객 계좌에 입금하고 거래 기록을 생성하며 수취를 `성공`으로 변경한다. `결제거절`을 받으면 수취 기록이 있을 때만 입금 없이 `실패`로 변경한다. 수취 기록이 없으면 새 기록을 만들지 않는다.
- 확인 조회는 결과가 확정되지 않은 기록만 대상으로 한다. 확정된 기록은 대상에서 제외한다.
- 송금 은행은 응답을 받지 못한 송금을 결제 만료 시간까지 `송금중`으로 유지하고, 만료 후 중앙 결제 시스템에 결과를 확인 조회한다. `결제완료`면 `성공`으로 변경한다. `결제거절`이면 보상한 뒤 `실패`로 변경한다. `수취검증대기`면 `송금중`을 유지한다.
- 결제 만료 전 확인 조회에서 기록이 없으면 송금 은행은 보상하지 않고 `송금중`을 유지한다.
- 결제 만료 후 중앙 결제 시스템의 권위 있는 확인 조회에서 기록이 없으면 송금 은행은 보상하고 송금을 `실패`로 변경한다. 연결 실패나 조회 실패는 `기록 없음`으로 취급하지 않는다.
- 지연된 최초 요청이 만료 후 도착하면 중앙 결제 시스템은 `결제거절`로 저장하고 새 결제를 시작하지 않는다.
- 같은 외부 거래 ID의 기존 기록이 있으면 중앙 결제 시스템은 거래 내용을 비교한다. 같은 내용이면 현재 상태를 반환하고, 다른 내용이면 최종 결제 결과가 아니라 내용 충돌로 요청을 거절한다.
- 수취 은행은 결제 결과 통지를 받지 못한 `수취중` 수취 기록의 결과를 중앙 결제 시스템에 확인 조회한다. `결제완료`면 입금, 입금 기록과 수취 성공을 하나의 로컬 DB 트랜잭션으로 반영한다. `결제거절`이거나 만료 후 중앙 기록이 없으면 입금 없이 `실패`로 변경한다. `수취검증대기`면 `수취중`을 유지한다.
- 중앙 결제 시스템은 수취 검증을 재요청하지 않는다. 검증 요청 실패나 제한 시간 초과가 발생하면 해당 `수취검증대기` 결제를 `결제거절`로 확정한다.
- 중앙 결제 시스템이 최종 상태로 변경할 때는 현재 상태가 `수취검증대기`인지 확인한다. 수취 가능 응답으로 완료할 때는 전체 결제 만료 여부도 다시 확인한다. 이미 확정된 상태는 다른 처리 결과로 덮어쓰지 않는다.
- 결과 불명의 복구는 미확정 기록을 가진 쪽이 수행한다. 송금 은행은 `송금중` 송금을, 수취 은행은 `수취중` 수취 기록을 확인 조회한다. 중앙 결제 시스템에 비정상적으로 남은 `수취검증대기` 결제는 검증을 재요청하지 않고 전체 결제 만료 규칙에 따라 `결제거절`로 종결한다.
- `결제완료`와 `결제거절`은 확정된 결과다. 중앙 결제 시스템은 수취 검증을 시도한 요청 흐름에서 최종 상태를 저장한 뒤 결과 통지를 한 번 시도한다. 처음 접수한 만료 요청, 기존 결제의 재요청과 복구 작업은 결과를 통지하지 않는다. 프로세스 중단으로 통지를 시도하지 못했거나 통지 요청이 유실되어도 결과를 다시 통지하지 않고 수취 은행의 반영 여부도 추적하지 않는다.
- 결제 결과 통지는 수취 은행의 응답을 업무 계약에 포함하지 않는다. 통신 계층의 응답이 존재하더라도 중앙 결제 결과, 재통지 또는 복구 여부를 판단하는 근거로 사용하지 않는다.
- 결제 결과 통지 요청이 수취 은행에 도달하지 않으면 수취 은행은 `수취중` 기록의 확인 조회를 통해 결과를 반영한다.
- 로컬 반영 규칙은 결제 결과가 동기 응답, 확인 조회, 대사 중 어떤 경로로 도착했는지에 의존하지 않는다.
- 송금 은행은 중앙 결제 결과를 근거로 자기 송금을 변경한다. 이 과정에서 송금 계좌를 다시 출금하지 않는다.
- 수취 은행은 중앙 결제 시스템이 완료로 확정한 거래만 고객 계좌에 입금으로 반영한다.
- 수취 은행의 로컬 반영 실패는 중앙 결제 결과를 변경하지 않으며, 동일한 중앙 결제 거래를 근거로 복구해야 한다.
- 결제 결과 통지와 확인 조회 결과가 같은 결제에 대해 겹쳐 도착해도 외부 거래 ID로 기존 로컬 반영 여부를 확인하고 잔액이나 수취 상태를 중복 변경하지 않는다.
- 은행의 송금·수취 상태는 중앙 결제 상태보다 늦게 반영될 수 있다. 확인 조회와 대사로 최종적으로 같아져야 한다.
- 중앙 결제의 완료·거절 결과 또는 만료 후 권위 있는 `기록 없음`의 근거 없이 고객 계좌에 입금하거나 보상하지 않는다.
- 은행은 정해진 주기로 자기 거래 기록과 중앙 결제 기록을 대조하는 대사를 수행한다. 대사 주기는 아직 결정하지 않았다. 대사는 결과 전달 수단이 아니라 정상 경로와 확인 조회가 모두 놓친 불일치를 탐지하는 안전망이다.
- 확인 조회는 결제 만료 후 시작한다. 조회가 실패하거나 중앙 결제가 아직 `수취검증대기`이면 상태를 확정하지 않고 이후 복구 실행에서 다시 확인한다. 복구로 확정된 결과를 고객에게 전달하는 별도 알림 기능은 현재 구현하지 않는다.

### 복구 실행과 배치 조회

- 송금 은행, 수취 은행과 중앙 결제 시스템은 각각 스케줄러로 복구 작업을 실행한다. `fixedDelay = 30초`이므로 앞선 실행이 끝난 뒤 30초를 기다리고 다음 실행을 시작한다.
- 각 실행은 시작 시각을 한 번 구하고 복구 대상의 시각 조건을 끝까지 고정한다. 조회는 로컬 기록의 `created_at`, `id` 오름차순으로 최대 100건씩 수행한다.
- 송금은 생성 후 300초가 지난 `송금중` 기록을 처리한다. 수취와 중앙 결제는 원래 송금 생성 후 300초가 지났고 현재 실행 시작 시각까지 생성된 미확정 기록을 처리한다.
- 마지막으로 읽은 `(created_at, id)` 다음부터 계속 읽으므로, 대기 상태로 남은 기록이 있어도 같은 실행에서 첫 페이지를 반복하지 않는다. 다음 스케줄러 실행은 읽은 위치를 초기화한다.
- 중앙의 복구 작업은 만료된 `수취검증대기`를 거절로 변경할 뿐, 수취 검증이나 결과 통지를 다시 요청하지 않는다.
- 은행은 한 묶음의 중앙 상태를 HTTP로 조회한 뒤 로컬 DB 트랜잭션 안에서 같은 송금 키들의 기록을 일괄 재조회하여 반영한다. 외부 조회는 이 트랜잭션에 포함하지 않는다.
- 배치 조회 API는 `GET /settlements:batchGetStates`이며 쿼리 파라미터로 `bankCode`와 1~100개의 `transferKeys`를 받는다. 여러 키는 같은 `transferKeys` 파라미터를 반복해 전달한다.
- 지정된 은행이 송금 은행 또는 수취 은행인 결제만 조회한다. 응답의 `states`는 송금 키를 키로 하고 중앙 결제 상태를 값으로 갖는 맵이다. 조회 범위에서 찾지 못한 키는 응답에서 생략하며, 찾은 기록이 없으면 빈 맵을 반환한다.
- 통신 실패, HTTP 오류, 빈 응답 본문 또는 응답 해석 실패는 조회 실패다. 빈 상태 맵이나 맵에 특정 키가 없는 경우와 구분하며, 조회 실패를 근거로 보상하거나 입금하지 않는다.
- 잠금과 동시에 도착한 결과의 원자적 반영은 별도의 동시성 작업에서 다룬다.

### 수취 기록의 상태

- 수취 기록의 상태는 `수취중`, `성공`, `실패`다.
- 최초 상태는 `수취중`이며 검증 요청을 받아 수취 가능을 응답할 때 기록한다. 수취 불가를 응답하는 요청은 수취 기록을 만들지 않는다.
- 결제 결과 통지 또는 확인 조회로 `결제완료`를 확인하고 고객 계좌 입금과 거래 기록 생성을 마치면 `성공`으로 변경한다.
- 결제 결과 통지 또는 확인 조회로 `결제거절`을 확인하면 입금 없이 `실패`로 변경한다.
- `성공`과 `실패`는 최종 상태다.
- 같은 외부 거래 ID의 수취 기록은 한 건만 존재한다. 중앙 결제 시스템이 의도적으로 검증을 재요청하지는 않지만 중복 요청이 도착하면 기존 기록으로 같은 응답을 한다.

### 대사

- 대사는 세 번째 안전망으로 둔다.
- 대조 대상, 대조 방식, 실행 방법은 아직 결정하지 않았다.

### 선택 이유

- 정상 거래는 송금 은행의 요청 한 번 안에서 결과까지 확정되므로 고객이 요청 응답으로 결과를 받는다.
- 수취 검증이 제한 시간 안에 끝나지 않으면 중앙 결제 시스템이 거절로 확정하므로 수취 은행 장애가 중앙의 미확정 작업과 재시도 부하로 계속 누적되지 않는다.
- 각 시스템이 저장을 마친 뒤에 호출하고 응답하므로, 다음 통신이 실패해도 이미 저장한 기록은 복구 근거로 남는다. 요청이 상대 시스템에 도달하지 않았다면 상대편에는 기록이 없을 수 있다.
- 결과 불명 건만 조회하므로 조회 대상이 작고, 정상 경로와 예외 경로가 분리되어 각각 독립적으로 관찰하고 개선할 수 있다.
- 실제 은행 간 송금이 같은 구조를 사용하므로 장애 복구와 부하 실험의 결과를 실제 사례와 비교할 수 있다.
- 결과 수신 경로와 로컬 반영을 분리하면 통신 방식을 바꾸더라도 계좌, 거래 기록과 멱등 반영 규칙을 다시 설계하지 않아도 된다.
- 중앙 결제 완료와 수취 은행의 고객 계좌 반영을 분리하여, 수취 은행 장애가 은행 간 결제의 최종성을 바꾸지 못하게 한다.
- 대사를 안전망으로 두면 정상 경로와 확인 조회의 누락이 있어도 정해진 주기 안에 탐지되고, 그 탐지 결과가 정상 경로의 결함을 찾는 근거가 된다.

### 파생 불변식

- 재전송, 확인 조회 재실행과 대사로 고객 계좌 잔액이 중복 변경되어서는 안 된다.
- 결과가 확정되지 않은 기록은 확인 조회와 대사 대상에 포함되어야 한다.
- 중앙 결제 거래의 로컬 반영 여부를 외부 거래 ID로 확인할 수 있어야 한다.
- 수취 은행의 로컬 반영 중 장애가 발생해도 같은 완료 거래를 중복 입금해서는 안 된다.

## 10. 요청 및 결제 거절 조건

### 결정

다음 경우에는 거래를 다음 단계로 진행하지 않는다.

- 송금액이 0 이하이거나 정수가 아닌 경우: 송금 은행이 요청을 거절한다.
- 송금 계좌 잔액이 부족한 경우: 송금 은행이 요청을 거절한다.
- 수취 계좌가 존재하지 않는 경우: 중앙 결제를 거절하고 수취 계좌에 입금하지 않는다.
- 수취 검증 요청이 실패하거나 수취 가능 응답을 제한 시간 안에 확인하지 못한 경우: 중앙 결제를 거절하고 수취 검증을 재요청하지 않는다.
- 송금 은행의 중앙 결제잔액이 부족한 경우: 중앙 결제를 거절한다.
- 중앙 결제 시스템이 처음 접수한 결제 요청이 이미 만료된 경우: `결제거절`로 기록하고 다음 단계로 진행하지 않는다.
- 동일한 외부 거래 ID가 기존 거래와 다른 내용으로 전달된 경우

### 선택 이유

- 유효하지 않은 금액과 고객 잔액을 초과한 송금을 사전에 막아 고객 잔액이 음수가 되는 것을 방지한다.
- 사전 거절은 돈이 이동한 거래가 아니므로 계좌 거래 내역에 포함하지 않는다.
- 수취 계좌가 없으면 입금 대상을 확정할 수 없으므로 은행 간 결제를 완료하지 않는다.
- 중앙 결제잔액을 초과한 결제를 막아 중앙 원장의 잔액이 음수가 되는 것을 방지한다.
- 외부 거래 ID의 내용 충돌은 정상 재시도가 아니므로 금액을 반영해서는 안 된다.
- 만료된 결제 요청을 중앙에서 확정적으로 거절하여 지연된 요청이 뒤늦게 자금을 이동시키는 것을 막는다.

### 제외 범위

- 계좌 정지 상태에 따른 입금 제한
- 계좌 삭제와 해지
- 통화 검증, 외화와 환전
- 송신 은행의 등록, 인증과 유효성 검증

## 11. 현재 확정된 핵심 불변식

1. 모든 고객 계좌는 정확히 한 명의 고객에게 소유되어야 한다.
2. 고객은 자신이 소유하지 않은 계좌에서 자금을 이동시킬 수 없다.
3. 은행은 다른 은행이나 중앙 결제 시스템의 DB를 직접 읽거나 수정하지 않는다.
4. 계좌의 현재 잔액은 삭제하거나 덮어쓰지 않은 거래 기록으로 설명할 수 있어야 한다.
5. 하나의 은행 간 결제 거래는 송금 계좌에서 한 번만 출금되어야 한다.
6. 하나의 중앙 결제 거래는 수취 계좌에 한 번만 입금되어야 한다.
7. 동일한 외부 거래 ID가 다른 거래 내용에 재사용되면 금액을 반영하지 않는다.
8. 송금 은행은 중앙 결제 결과를 확인할 수 없다는 이유만으로 거래를 추측하여 실패 처리하거나 보상하지 않는다. 중앙 결제 시스템이 수취 검증 제한 시간에 따라 확정한 `결제거절`은 추측이 아니라 권위 있는 최종 결과다.
9. 은행의 로컬 반영은 그 근거가 된 중앙 결제 거래까지 추적할 수 있어야 한다.
10. 재전송, 확인 조회와 대사를 포함한 여러 처리 시도에도 동일한 거래가 중복 반영되어서는 안 된다.
11. 중앙 결제 전후 모든 은행 결제계좌 잔액의 합계는 보존되어야 한다.
12. 중앙 결제 시스템이 완료로 확정한 거래를 개별 은행이 실패나 거절로 되돌려서는 안 된다.
13. 수취 은행의 수취 가능 확인이 없는 거래를 중앙 결제 완료로 변경해서는 안 된다.
14. 송금액은 0보다 큰 정수여야 한다.
15. 고객 계좌와 은행 결제계좌의 잔액은 송금 처리로 인해 0보다 작아져서는 안 된다.
16. 은행 내부 이체, 송금 출금과 수취 입금은 각각 그 금액 변동을 설명하는 거래 기록을 가져야 한다.
17. 만료 전에 접수한 중앙 결제 거래는 `수취검증대기`에서 하나의 최종 상태인 `결제완료` 또는 `결제거절`로만 확정되어야 한다. 처음 접수할 때 이미 만료된 요청은 `결제거절`로 생성한다. 어떤 경로든 최종 상태는 변경하지 않는다.
18. 대사는 은행의 로컬 상태를 중앙 결제 기록에 맞춰 수렴시킬 뿐 중앙 결제 결과를 변경해서는 안 된다.
19. 결제 시간이 만료된 `수취검증대기` 결제는 `결제거절`로 처리해야 한다. 만료 처리가 지연되는 동안에도 수취 가능 응답으로 `결제완료`가 되어서는 안 된다.
20. 같은 결제를 재전송할 때 외부 거래 ID, 송금 생성 시각과 거래 내용은 변경해서는 안 된다.
