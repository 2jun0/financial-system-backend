# 데이터 모델

이 문서는 현재 합의된 데이터 모델과 제약조건을 기록한다.

전체 관계는 [ERD](erd.md)에서 확인한다.

## Customer

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 고객의 내부 식별자 | 고유 식별자 |
| `login_id` | 회원가입과 로그인에 사용하는 식별자 | 은행 시스템 안에서 고유, 필수 |
| `password_hash` | 단방향 해시된 비밀번호 | 필수, 평문 비밀번호 저장 금지 |
| `created_at` | 생성 시각 | 필수, 생성 후 변경 금지 |
| `updated_at` | 수정 시각 | 필수 |

## Account

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 계좌의 내부 식별자 | 고유 식별자 |
| `account_number` | 고객과 은행 간 송금에서 사용하는 UUID 계좌번호 | 고유, 필수, 생성 후 변경 금지 |
| `customer_id` | 계좌를 소유한 고객의 내부 식별자 | 필수, `Customer.id` 참조 |
| `name` | 계좌 이름 | 필수 |
| `balance` | 현재 잔액 | 송금 처리로 인해 음수가 될 수 없음 |
| `created_at` | 생성 시각 | 필수, 생성 후 변경 금지 |
| `updated_at` | 수정 시각 | 필수 |

## AccountTransaction

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 계좌 거래 기록의 내부 식별자 | 고유 식별자 |
| `account_id` | 잔액이 변경된 계좌의 내부 식별자 | 필수, `Account.id` 참조 |
| `transfer_key` | 잔액 변경을 발생시킨 시스템 간 공유 송금 키 | 필수, 재시도에도 유지 |
| `other_bank_code` | 상대 계좌가 속한 은행의 식별자 | 필수, 내부 이체에는 현재 은행 코드 기록 |
| `other_account_number` | 상대 계좌번호 | 필수 |
| `amount` | 해당 계좌의 잔액 변화량 | 0 금지, 출금은 음수, 입금과 보상은 양수 |
| `type` | 계좌 잔액 반영 종류 | `DEBIT`, `CREDIT`, `COMPENSATION` 중 하나 |
| `created_at` | 거래 기록 생성 시각 | 필수 |

### 계좌 거래 기록 제약

- `transfer_key`는 DB 트랜잭션 식별자가 아니라 하나의 자금 이동을 식별하는 시스템 간 공유 키다.
- 은행 간 송금에서는 송금 은행, 중앙 결제 시스템과 수취 은행이 같은 `transfer_key`를 사용한다.
- 동일한 자금 이동을 재시도하거나 다시 조회해도 `transfer_key`를 변경하지 않는다.
- 시연용 고객 계좌에서 신규 계좌로 보내는 내부 이체에도 하나의 `transfer_key`를 발급해 양쪽 거래 기록을 연결한다.
- 한 은행 DB에서 `(transfer_key, type)` 조합은 고유해야 한다.
- `DEBIT`의 `amount`는 음수여야 한다.
- `CREDIT`과 `COMPENSATION`의 `amount`는 양수여야 한다.
- 시연용 내부 이체는 출발 계좌에 `DEBIT`, 신규 계좌에 `CREDIT`으로 기록한다.
- 은행 간 송금은 송금 계좌에 `DEBIT`, 수취 계좌에 `CREDIT`으로 기록한다.
- 중앙 결제거절에 따른 출금 반환은 `COMPENSATION`으로 기록한다.
- 계좌 거래 기록은 송금의 최종 완료 시점이 아니라 해당 계좌의 잔액이 실제로 변경되는 시점에 생성한다.
- 송금을 시작하며 선출금하면 송금 상태가 `송금중`이어도 출금 기록을 즉시 생성한다.
- 결제거절로 출금액을 반환하면 별도의 보상 기록을 생성한다.
- 수취 은행은 완료된 중앙 결제를 고객 계좌에 실제 반영할 때 입금 기록을 생성한다.
- 잔액 변경과 그 근거가 되는 계좌 거래 기록 생성은 하나의 로컬 DB 트랜잭션으로 처리한다.
- 거래 기록은 잔액 변경의 근거이므로 생성 후 수정하거나 삭제하지 않는다.
- `label`은 MVP에 포함하지 않는다.

## Transfer

송금 은행이 고객의 은행 간 송금 요청과 진행 상태를 관리한다.

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 송금 은행 DB 내부의 송금 식별자 | auto increment PK |
| `transfer_key` | 송금 은행과 중앙 결제 시스템이 공유하는 송금 키 | 고유, 필수, 변경 금지, 재시도에도 유지 |
| `source_account_id` | 출금할 고객 계좌의 내부 식별자 | 필수, `Account.id` 참조 |
| `recipient_bank_code` | 수취 은행 식별자 | 필수 |
| `recipient_account_number` | 수취 계좌번호 | 필수 |
| `amount` | 송금 요청 금액 | 0보다 큰 정수 |
| `state` | 송금 진행 상태 | `송금중`, `성공`, `실패` 중 하나 |
| `created_at` | 송금 생성 시각 | 필수, 생성 후 변경 금지 |
| `updated_at` | 송금 상태가 마지막으로 변경된 시각 | 필수 |

### 송금 식별자 제약

- `Transfer.id`는 송금 은행 DB 내부의 auto increment PK다.
- `Transfer.transfer_key`는 송금 은행과 중앙 결제 시스템 사이에서 같은 송금을 식별하는 업무 키다.
- 중앙 결제 요청을 재시도해도 `transfer_key`를 변경하지 않는다.
- 계좌 거래 기록의 `AccountTransaction.transfer_key`도 같은 값을 사용한다.
- 고객이 송금 은행에 보내는 요청의 별도 `idempotency_key`는 현재 모델에 포함하지 않는다.

## Receipt

수취 은행이 계좌 검증을 통과해 승인하기로 한 결제의 수취 진행 상태를 관리한다. 계좌가 없어 거절하는 요청은 `Receipt`를 생성하지 않는다.

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 수취 은행 DB 내부의 수취 식별자 | auto increment PK |
| `transfer_key` | 송금 은행·중앙 결제 시스템·수취 은행이 공유하는 송금 키 | 고유, 필수, 변경 금지, 재시도에도 유지 |
| `recipient_account_id` | 입금할 고객 계좌의 내부 식별자 | 필수, `Account.id` 참조 |
| `source_bank_code` | 송금 은행 식별자 | 필수 |
| `source_account_number` | 송금 계좌번호 | 필수 |
| `amount` | 수취 금액 | 0보다 큰 정수 |
| `state` | 수취 진행 상태 | `RECEIVING`, `SUCCEEDED`, `FAILED` 중 하나 |
| `created_at` | 수취 기록 생성 시각 | 필수, 생성 후 변경 금지 |
| `updated_at` | 수취 상태가 마지막으로 변경된 시각 | 필수 |

### 생성 및 복구 규칙

- 수취 계좌가 존재함을 확인한 뒤, 중앙에 승인 요청을 보내기 전에 `Receipt`를 저장하고 커밋한다.
- 같은 결제를 다시 조회해도 동일한 `transfer_key`의 수취 기록을 중복 생성하지 않는다.
- 수취 은행은 로컬의 `RECEIVING` 기록을 대상으로 중앙 결제 결과를 조회한다.
- 기록 저장 후 승인 요청 전에 장애가 발생해도, 남아 있는 수취 기록을 이용해 필요한 승인 요청을 재전송할 수 있어야 한다.
- 중앙의 전체 결제완료 이력을 반복 조회하거나 중앙에 별도의 수취 반영 완료 ACK를 보내는 방식은 사용하지 않는다.

### 수취 상태 규칙

- `수취중`, `성공`, `실패`는 각각 `RECEIVING`, `SUCCEEDED`, `FAILED`로 표현한다.
- 최초 상태는 `RECEIVING`이며, 승인 요청 전부터 고객 계좌 입금이 완료되기 전까지를 포함한다.
- 중앙 결제가 `SETTLED`이면 고객 계좌에 입금하고 `SUCCEEDED`로 변경한다.
- 계좌 잔액 증가, 동일한 `transfer_key`의 `CREDIT` 거래 기록 생성, `Receipt`의 `SUCCEEDED` 변경은 하나의 로컬 DB 트랜잭션으로 처리한다.
- `SUCCEEDED`는 중앙 결제완료 확인만이 아니라 수취 고객 계좌 입금까지 완료했다는 의미다.
- 중앙 결제가 `REJECTED`로 확정되면 입금 없이 `FAILED`로 변경한다. 수취 은행이 승인하기로 한 건도 중앙에서 결제거절될 수 있다.
- 승인 요청·결제 결과 조회의 통신 실패, 중앙의 수취검증대기 상태, 로컬 입금 처리 실패만으로 `FAILED`로 변경하지 않고 `RECEIVING`을 유지한다.
- 완료된 수취를 다시 처리해도 고객 계좌에 중복 입금하지 않는다.

### 완료 기록 보관

- 현재 설계에서는 `Transfer`와 `Receipt`의 성공·실패 기록을 삭제하지 않고 보관한다.
- 후속 처리는 미완료 기록만 대상으로 하며, 완료 기록의 보관을 이유로 전체 이력을 반복 조회하지 않는다.

## Bank

중앙 결제 시스템에 참가하는 은행과 그 은행의 현재 결제잔액을 관리한다.

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 중앙 결제 DB 내부의 참가 은행 식별자 | auto increment PK |
| `bank_code` | 은행과 중앙 결제 시스템이 사용하는 은행 식별자 | 고유, 필수 |
| `balance` | 참가 은행의 현재 결제잔액 | 필수, 결제로 인해 음수가 될 수 없음 |
| `created_at` | 참가 은행 등록 시각 | 필수, 생성 후 변경 금지 |
| `updated_at` | 참가 은행 정보나 결제잔액이 마지막으로 변경된 시각 | 필수 |

### 결제잔액 저장 방식

- 참가 은행마다 원화 결제잔액 하나만 관리한다.
- 별도의 `SettlementAccount` 모델을 만들지 않고 `Bank.balance`에 현재 결제잔액을 저장한다.
- 중앙 결제 거래의 완료 시 송금 은행 참가자의 잔액을 차감하고 수취 은행 참가자의 잔액을 증가시킨다.
- 두 참가자의 잔액 변경과 중앙 결제 거래의 완료는 하나의 중앙 DB 트랜잭션으로 처리한다.

## Settlement

중앙 결제 시스템이 은행 간 결제의 진행 상태와 최종 결과를 관리한다.

| 속성 | 의미 | 확정된 제약 |
|---|---|---|
| `id` | 중앙 결제 DB 내부의 결제 거래 식별자 | auto increment PK |
| `transfer_key` | 송금 은행과 중앙 결제 시스템이 공유하는 송금 키 | 고유, 필수, 변경 금지 |
| `source_bank_id` | 송금 은행의 중앙 결제 내부 식별자 | 필수, `Bank.id` 참조 |
| `source_account_number` | 송금 고객 계좌번호 | 필수, 참조 정보 |
| `recipient_bank_id` | 수취 은행의 중앙 결제 내부 식별자 | 필수, `Bank.id` 참조 |
| `recipient_account_number` | 수취 고객 계좌번호 | 필수, 참조 정보 |
| `amount` | 중앙 결제 금액 | 0보다 큰 정수 |
| `state` | 중앙 결제의 진행 상태와 최종 결과 | `RECIPIENT_VALIDATION_PENDING`, `SETTLED`, `REJECTED` 중 하나 |
| `created_at` | 중앙 결제 거래 생성 시각 | 필수, 생성 후 변경 금지 |
| `updated_at` | 중앙 결제 상태가 마지막으로 변경된 시각 | 필수 |

### 상태 규칙

- 도메인 문서의 `수취검증대기`, `결제완료`, `결제거절`은 각각 `RECIPIENT_VALIDATION_PENDING`, `SETTLED`, `REJECTED`로 저장한다.
- 최초 상태는 `RECIPIENT_VALIDATION_PENDING`이다.
- 수취 은행이 수취 가능을 확인하면 `SETTLED`로 변경한다.
- 수취 은행이 수취 불가를 확인하면 `REJECTED`로 변경한다.
- `SETTLED`와 `REJECTED`는 서로 되돌리거나 다른 최종 상태로 변경할 수 없는 최종 상태다.
- `SETTLED`는 두 은행의 결제잔액 이동이 완료됐다는 의미이며 수취 고객 계좌 입금 완료를 의미하지 않는다.
- `SETTLED` 전이, 송금 은행 `Bank.balance` 차감과 수취 은행 `Bank.balance` 증가는 하나의 중앙 DB 트랜잭션으로 처리한다.
- `REJECTED`로 확정할 때는 두 은행의 결제잔액을 변경하지 않는다.
- 동일한 `transfer_key`로 둘 이상의 중앙 결제 거래를 생성하지 않는다.
- `source_bank_id`와 `recipient_bank_id`는 서로 달라야 한다.
- 중앙 결제 시스템은 고객 계좌번호를 거래 식별과 수취 검증을 위한 참조 정보로만 저장하며 고객 계좌나 잔액을 소유하지 않는다.

## 모델 용어 규칙

- 자금 이동은 `transfer`로 표현한다.
- 수취 은행의 수취 처리 기록은 `Receipt`로 표현한다.
- 돈이 나가는 쪽은 `source_*`로 표현한다.
- 돈을 받는 쪽은 `recipient_*`로 표현한다.
- 방향이 정해진 모델에서는 `sender_*`, `receiver_*`, `destination_*`, `target_*`를 같은 의미로 섞어 쓰지 않는다.
- 계좌 거래 기록처럼 한 계좌 관점에서 입금·출금 방향이 달라지는 모델의 상대편은 `other_*`로 표현한다.

## 관계

- 한 고객은 여러 계좌를 소유할 수 있다.
- 모든 계좌는 정확히 한 고객에게 소유된다.
- 한 계좌는 여러 계좌 거래 기록을 가질 수 있다.
- 하나의 자금 이동은 반영 종류가 서로 다른 여러 계좌 거래 기록을 만들 수 있다.
- `Transfer`는 송금 요청의 진행 상태를, `AccountTransaction`은 계좌에 실제 반영된 잔액 변화를 표현한다.
- 하나의 `Transfer`는 동일한 `transfer_key`로 여러 `AccountTransaction`과 연결될 수 있다.
- 한 계좌는 여러 `Receipt`의 수취 계좌가 될 수 있다.
- `Receipt`는 수취 처리의 진행 상태를 표현하며, 성공 시 같은 `transfer_key`의 `CREDIT` 거래 기록과 연결된다.
- 송금 은행의 `Transfer`, 중앙의 `Settlement`, 수취 은행의 `Receipt`는 서로 다른 DB에 저장되며 같은 `transfer_key`로 연결된다. 시스템 간 DB 외래키는 두지 않는다.
- `Settlement`는 송금 은행과 수취 은행을 각각 `Bank`로 참조한다.
- 시연용 고객과 시연용 계좌도 동일한 `Customer`, `Account` 모델을 사용하며 별도 계좌 유형을 두지 않는다.

## 계좌번호 규칙

- 계좌 생성 서비스의 계좌번호 생성기가 임의의 UUID를 `account_number`로 발급한다.
- 생성기는 발급한 계좌번호를 `Account.create`에 전달하고, `Account`는 직접 무작위 값을 생성하지 않는다.
- `account_number`는 은행 DB 안에서 고유하고 반드시 존재해야 한다.
- UUID 충돌 가능성과 무관하게 DB 고유 제약을 둔다.
- 한 번 발급한 `account_number`는 변경하지 않는다.
- 은행 간에는 `bank_code`와 `account_number`의 조합으로 계좌를 지정한다.
- UUID는 숫자 계산 대상이 아니며 고객과 시스템이 사용하는 계좌 식별자다.

## 선택 이유

- 내부 저장 식별자인 `Account.id`와 고객 및 은행 간 송금에서 사용하는 계좌번호의 역할을 분리한다.
- 시연용 데이터 때문에 계좌 도메인에 별도 계좌 유형이나 소유 관계 예외를 추가하지 않는다.
