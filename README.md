# Financial System Backend

금융 거래에서 발생하는 데이터 정합성, 동시성, 트랜잭션, 멱등성, 장애 복구 문제를 직접 재현하고 해결하는 백엔드 프로젝트입니다.

특정 기술을 먼저 정해 적용하기보다 문제를 발견하고, 설계하고, 실패를 검증한 뒤 개선하는 과정을 중요하게 다룹니다.

## 진행 원칙

> 문제 발견 → 직접 설계 → 구현 → 실패 및 검증 → 개선

- AI가 설계를 대신하게 하지 않습니다.
- AI는 작성한 설계의 반례 탐색, 기술 검토, 대안 비교를 위한 조언 도구로 활용합니다.
- ERD와 API를 먼저 만들기보다 시스템이 반드시 지켜야 할 불변식을 먼저 정의합니다.
- 최종 결과뿐 아니라 실패한 설계, 비교한 대안, 선택 근거와 측정 결과를 기록합니다.

## 8주 계획

### 1주차 — 도메인/불변식 설계

금융 거래의 규칙, 상태, 실패 조건을 직접 정의합니다. ERD와 API보다 먼저 “절대 깨지면 안 되는 조건”을 명시합니다.

### 2주차 — 최소 거래 시스템 구현

입금·출금·송금을 구현합니다. 일부러 단순하게 만들어 이후 깨뜨리고 개선할 기반을 만듭니다.

### 3주차 — 트랜잭션과 정합성

부분 실패를 실제로 재현합니다. 트랜잭션 경계를 여러 방식으로 고민하고 선택 이유까지 기록합니다.

### 4주차 — 동시성 제어 실험

Race condition을 재현하고, 두 개 이상의 대안을 직접 구현해 비교합니다. 정합성뿐 아니라 성능도 측정합니다.

### 5주차 — 멱등성과 재시도

중복 요청, timeout, 응답 유실을 재현합니다. “처리는 됐지만 클라이언트는 실패로 인식하는 상황”까지 다룹니다.

### 6주차 — 장애 복구와 외부 시스템

외부 I/O 실패와 DB commit 전후 장애를 다룹니다. 재처리 전략과 transaction boundary를 다시 설계합니다.

### 7주차 — 공격적 검증

동시 요청, 장애, 중복, 부하 테스트를 수행합니다. 정의한 불변식이 깨지는 조건을 계속 찾고 성능 trade-off까지 확인합니다.

### 8주차 — 리팩토링 + 설계 기록

“무엇을 구현했는가”보다 아래 흐름을 보여주는 사례 3~5개를 정리합니다.

> 문제 → 최초 설계 → 실패 → 대안 → 선택 → 측정 결과

## 현재 단계

1주차 도메인/불변식 설계를 시작합니다. 기술 스택과 구현 구조는 문제와 요구사항을 정의한 뒤 선택합니다.
